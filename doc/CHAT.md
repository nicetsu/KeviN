## 1 · หลักการที่ทุกอย่างตามมา

### เสียงไม่ใช่ระบบใหม่ · เป็นอีกช่องทางของสมองตัวเดียวกัน

โหมดเสียงกับโหมดแชตใช้โมเดลคนละตัวและต่อคนละแบบ แต่**เวลาจะอ่านข้อมูลจริง ลงมาที่ `registry.run()` ตัวเดียวกัน**
ต่างกันแค่ว่าใครเป็นคนเรียก · prompt เดียว บุคลิกเดียว ประวัติกองเดียว

### read-only ทำให้ปัญหาที่ยากที่สุดหายไปทั้งหมด

สิ่งที่เคยเป็นส่วนยากที่สุดของดีไซน์รอบก่อน ๆ **ไม่ต้องทำแล้วสักข้อ** —
ร่าง+ยืนยันก่อนเขียน · สามชั้นความเสี่ยงของ tool · กลัวโมเดลฟังภาษาไทยผิดแล้วเขียนผิด ·
กลัว “ไม่ไป” ปนกับ “ไม่มีคาบ” · สมุดบันทึกการเขียน

เหลือกฎข้อเดียว และบังคับได้ที่ระดับโครงสร้าง: **ไม่มี tool ตัวไหนที่เขียนได้**

### คำปฏิเสธต้องกลายเป็นทางลัด ไม่ใช่ทางตัน

ผู้ช่วยที่แก้อะไรไม่ได้จะน่าหงุดหงิดมาก ถ้ามันตอบแค่ “ทำให้ไม่ได้”

แต่**เว็บแอปนี้แก้ได้ทุกอย่างอยู่แล้ว และทุกหน้ามี URL** — ซึ่งเป็นเหตุผลที่หน้ากิจกรรมถูกทำเป็น route
ตั้งแต่แรก (ดู `DECISIONS.md` หัวข้อกิจกรรม) · คำปฏิเสธจึงมาพร้อมการ์ดที่พาไปหน้าที่แก้ได้ กดครั้งเดียวถึงที่หมาย

## 3 · ทำไม tool call ของเสียงต้องเด้งผ่านเบราว์เซอร์

**Live API รัน tool ที่ฝั่ง client** — โมเดลส่ง `BidiGenerateContentToolCall` มาให้
แล้ว**เราต้องเรียกเองและส่ง `FunctionResponse` กลับ** ไม่มีการจัดการอัตโนมัติแบบ `generateContent`

ทางที่ง่ายกว่าคือให้เบราว์เซอร์ถาม Supabase ตรง ๆ ด้วย anon key **ซึ่งห้ามทำ** เพราะจะข้ามตัวกรอง Area
เบราว์เซอร์จึงยิงเข้า `/api/read/*` ของเราเสมอ แล้วเซิร์ฟเวอร์เป็นคนถาม DB

> ⚠️ tool ต้องประกาศตอน**เปิด session** และ**แก้กลางสายไม่ได้** · ชุด tool ของเราคงที่อยู่แล้ว ไม่เป็นปัญหา

### หนึ่งรอบของการถาม

| | โหมดโทร | โหมดแชต |
|---|---|---|
| 1 | พูด → PCM16 → ws | พิมพ์ → `POST /api/chat` |
| 2 | VAD ตัดสินว่าพูดจบ · โมเดลคิด | ประวัติ + prompt (cache) → โมเดล |
| 3 | **ToolCall → กลับมาที่เบราว์เซอร์ → `/api/read/*`** | **functionCall → เรียกในเซิร์ฟเวอร์ตัวเอง** |
| 4 | `registry.run()` → Supabase → JSON | `registry.run()` → Supabase → JSON |
| 5 | `FunctionResponse` → กลับเข้าสาย | วนกลับเข้าโมเดล |
| 6 | เสียงตอบ 24kHz → ลำโพง | stream ข้อความกลับ |

แถวที่ 3 คือจุดเดียวที่ต่างกันจริง ๆ · รอบ tool ระหว่างสาย ≈ **150–250 ms** จากไทย
(เบราว์เซอร์ → Vercel โตเกียว → Supabase โตเกียว → กลับ)

## 4 · โมเดลและโควตา

free tier คิดโควตา **แยกรายโมเดล** — จงใจให้สองช่องทางใช้คนละตัว
**คุยเสียงจนหมดโควตาวันนั้น แชตยังใช้ได้ปกติ** และกลับกัน

| ช่องทาง | โมเดล | ต่อยังไง | ใช้จริง/วัน |
|---|---|---|---|
| เสียง | `gemini-3.1-flash-live-preview` | เบราว์เซอร์ ↔ Google ตรง (ephemeral token) | ~3–5 สาย |
| แชต | `gemini-3.1-flash-lite` | ผ่าน Route Handler ของเรา | ~20–50 ครั้ง |

### เพดานที่เหลือเป็นเพดานของแอปหลายคน ไม่ใช่ของผู้ใช้คนเดียว

| เพดาน | ค่าที่ให้มา | เราจะใช้ | ชนไหม |
|---|---|---|---|
| สายพร้อมกัน | 3–5 | 1 | ไม่มีทาง |
| คำขอต่อวัน | 250–1,500 | ~5 | ห่างสองหลัก |
| โทเคนต่อนาที | 250,000 | ~3,000 | ต้องคุย 80 สายพร้อมกัน |
| **ความยาวสาย** | **15 นาที** | คุยยาวได้ | ⚠️ **ข้อเดียวที่ต้องเขียนโค้ดรับมือ** |

> ✅ **ยืนยันแล้ว 30 ส.ค.** — บัญชีนี้เรียก Live API ได้ใน free tier จริง
> (ต่อ WebSocket ได้ `setupComplete` · โมเดลเรียก tool และตอบเสียงกลับมา 31 ก้อน)
> ตัวเลขเพดานยังมาจากแหล่งผสม (ที่เป็นของ Google จริงคือ firebase.google.com)
> แต่ข้อสรุป “ผู้ใช้คนเดียวไม่ชนเพดาน” ไม่เปลี่ยนแม้ตัวเลขจะแกว่งทั้งช่วง

### อายุของสาย — รายละเอียดที่ใช้ประโยชน์ได้

```
token หนึ่งใบ ────────────── ใช้ได้ 30 นาที ──────────────►
[ สายที่ 1 · 15 นาที ]───handle───[ สายที่ 2 · ต่อด้วย handle เดิม ]
0                              15 นาที                        30 นาที
```

**token อายุ 30 นาที ยาวกว่าสายหนึ่งเส้นเท่าตัว** → ต่อสายรอบแรก**ไม่ต้องวิ่งกลับมาขอ token ใหม่**
จึงต่อได้เร็วพอที่ผู้ใช้จะไม่รู้สึกว่าสายขาด

**เก็บ `sessionResumption` handle ไว้ตลอดสาย ไม่ใช่ตอนใกล้ครบ 15 นาที** — เน็ตหลุดกลางทางก็ต่อด้วยอันเดียวกัน

## 5 · เส้นแบ่งข้อมูล

| สิ่งนั้น | ข้ามไป Google ไหม | เพราะ |
|---|---|---|
| เสียงที่พูด · ข้อความที่พิมพ์ | **ข้าม** | เป็นอินพุตของโมเดลโดยตรง เลี่ยงไม่ได้ |
| ตารางเรียน · กิจกรรม · งาน | **ข้าม** | เป็นผลของ tool ที่โมเดลต้องใช้ตอบ |
| Area ทั้งสี่ (`Class` `Competition` `Personal` `General`) | **ข้าม** | เจ้าของเปิดให้เห็นครบ 31 ส.ค. · ยืนยันว่าไม่มีข้อมูลสำคัญ |
| Area ที่สร้างใหม่วันหน้า | **ไม่ข้าม** จนกว่าจะเติมชื่อเอง | allowlist ซ่อนของที่ไม่รู้จักไว้ก่อนเสมอ |
| รหัสผ่าน · session · key | **ไม่ข้าม** | ไม่เคยอยู่ในเส้นทางนี้ |

**ตัวกรอง Area อยู่ใน `registry.run()` ฝั่งเซิร์ฟเวอร์** — ทั้งสองช่องทางผ่านจุดนี้ จึงข้ามไม่ได้

> ตอนนี้เปิดครบทุก Area ตัวกรองจึงไม่ได้กรองอะไรในทางปฏิบัติ · **แต่กลไกต้องอยู่**
> เพราะมันคือสิ่งที่ทำให้ Area ที่สร้างใหม่วันหน้าไม่รั่วออกไปเอง

> ⚠️ **ราคาที่แท้จริงของคำว่าฟรี ไม่ใช่โควตา**
> เงื่อนไข free tier ระบุว่า Google เอาสิ่งที่ส่งไป **ไปพัฒนาผลิตภัณฑ์** และเตือนไว้เองว่าอย่าส่งข้อมูลส่วนตัวเข้ามา
> (paid tier ระบุตรงข้าม คือไม่เอาไปพัฒนาโมเดล)
>
> และตัวกรองแก้ให้ไม่ได้ทั้งหมด — มันกรอง *ข้อมูลที่ tool ตอบกลับ* ไม่ได้กรอง *คำถามที่พูดออกไป*
> ถ้าพูดว่า “เดือนนี้ใช้เงินไปเท่าไหร่” ประโยคนั้นถึง Google แล้วแม้ระบบจะปฏิเสธไม่ตอบ

## 6 · สามชั้นที่กันการเขียน

| ชั้น | อยู่ที่ | กันยังไง |
|---|---|---|
| 1 | `lib/ai/tools.ts` | ไม่มี tool ที่เขียนอยู่ในชุดเลย **โมเดลเรียกไม่ได้เพราะไม่มีชื่อให้เรียก** |
| 2 | `lib/ai/db.ts` + `/api/read/*` | `ReadOnlyDb` ไม่มีเมธอดเขียน **โค้ดที่พยายามเขียนคอมไพล์ไม่ผ่าน** · endpoint รับเฉพาะชื่อในทะเบียน |
| 3 | `test/guard.test.ts` | ด่านอัตโนมัติ — อ่านซอร์สจริงแล้วพังทันทีถ้ามีทางเขียนโผล่เข้ามาใน `lib/ai/**` |

### ชั้นที่ 3 ไม่ใช่ role ของ Postgres — และนี่คือเหตุผล

ร่างแรกวางไว้ว่าชั้นที่ 3 จะเป็น role ที่ DB ปฏิเสธการเขียนเอง · **เปลี่ยนแล้ว** ด้วยเหตุผลสามข้อ

**หนึ่ง — สถาปัตยกรรมไม่เอื้อ** JWT ใบเดียวถูกใช้ทั้งแอป ตอนกดติ๊กงานเสร็จกับตอนผู้ช่วยอ่านปฏิทิน
ใช้ token ใบเดียวกัน · Custom Claims ของ Supabase ฝัง claim ตอนล็อกอิน จึงแยกสองกรณีนี้ไม่ได้
ต้องมินต์ JWT ใบที่สองเองซึ่งแปลว่าต้องถือกุญแจเซ็นเอง

**สอง — มันจะเก็บภาษีทุก migration ในอนาคต** ทุกตารางใหม่ต้องเพิ่ม policy ให้ role นั้นเสมอ
ลืมเมื่อไหร่ผู้ช่วยจะมองไม่เห็นตารางนั้น **โดยไม่มี error** แล้วตอบว่า "ไม่มีข้อมูล" อย่างมั่นใจ —
เป็นความพังแบบ *ถูกบนจอ ผิดข้างใน และเงียบ* ซึ่งเป็นสิ่งที่โปรเจกต์นี้หลีกเลี่ยงที่สุด
และเจ้าของบอกว่าจะให้ Claude แก้ DB อีกเรื่อย ๆ ภาษีข้อนี้จึงเก็บไปตลอด

**สาม — มันกันได้แค่ประตูเดียว** ประตู MCP ต่อตรงเข้า Supabase ด้วย OAuth ของเจ้าของ
และ**เขียนได้เต็มที่ด้วย SQL ดิบอยู่แล้วโดยตั้งใจ** · role อ่านอย่างเดียวจึงไม่ได้ทำให้
"ฐานข้อมูลปลอดภัยจากการเขียน" แค่ทำให้เส้นทางที่วันนี้เขียนไม่ได้อยู่แล้ว เขียนไม่ได้อีกชั้น

**สิ่งที่กลัวจริง ๆ คือ "อนาคตมีคนเผลอเติมทางเขียนเข้ามาในชั้น tool"** ซึ่ง `test/guard.test.ts`
จับได้ตรงจุดนั้นในราคาเศษเสี้ยว และไม่มีอะไรต้องดูแลเพิ่ม

> ⚠️ **ยอมรับตรง ๆ ว่านี่ไม่ใช่การันตีของ DB** ถ้าวันหนึ่งมีคนแก้โค้ดพร้อมแก้เทสต์ ก็ทะลุได้
> ถ้าอยากได้การันตีจริงต้องกลับไปทำ role + JWT ใบที่สอง พร้อมจ่ายภาษีข้อสอง

### บอกด้วยว่ามีของที่มองไม่เห็น

`runTool()` คืน `hidden` = จำนวนแถวที่ตัวกรอง Area ตัดออก · prompt สั่งให้พูดออกมาเมื่อมากกว่า 0
เช่น "มีอีก 2 อันที่ผมดูไม่ได้" **โดยไม่บอกว่าเป็นอะไร**

ไม่งั้นตัวกรองที่ fail-closed จะทำให้ผู้ช่วยตอบว่า "ไม่มีอะไร" ทั้งที่ความจริงคือ "มี แต่ผมดูไม่ได้"
ซึ่งเป็นคนละเรื่องกัน — หลัก UX ข้อ 5 ข้อเดียวกับที่ใช้ตัดสินเรื่อง `skipped` บนปฏิทิน

## 7 · ข้อยกเว้นของ TRAPS.md ที่ตั้งใจ

`TRAPS.md` เขียนว่า **“ถ้าทำแชตในแอปเอง — API key ห้ามอยู่ฝั่ง PWA · ต้องผ่าน Edge Function เสมอ”**

เจตนาของกฎคือ **“key ห้ามอยู่ฝั่งเบราว์เซอร์”** ซึ่ง Vercel ฝั่งเซิร์ฟเวอร์ก็ตอบโจทย์เต็มที่
ตอนเขียนกฎยังไม่มีเซิร์ฟเวอร์ Next.js ในระบบ · ตอนนี้มีแล้วและได้ของแถมสามอย่าง

- **อยู่ `hnd1` ติดกับ DB** — tool ที่เรียกระหว่างสายวิ่งในโตเกียวทั้งขา

Route Handler ต้องตั้ง `runtime = 'nodejs'` และอยู่ใต้ `vercel.json` region `hnd1` เหมือนที่เหลือ

## 8 · UX

### แถบล่าง — ปมที่ต้องแก้ก่อน

หน้าวันนี้มี **ปุ่ม + สีม่วงอยู่มุมขวาล่างแล้ว** ถ้าปุ่มกลางเป็นวงกลมม่วงยกขึ้นแบบที่แอปส่วนใหญ่ทำ
จะได้วงกลมม่วงสองวงห่างกันไม่ถึงนิ้ว แย่งกันเป็นปุ่มหลัก และขัดกฎ **“ม่วงคือสิ่งที่กดได้”**
เพราะกฎนั้นไม่มีความหมายเมื่อมีม่วงสองก้อนคนละระดับความสำคัญ

```
วันนี้ · ปฏิทิน · [ KeviN ] · คลัง · ตั้งค่า
                    ▲
        แคปซูลพื้นม่วงจาง ไม่ใช่วงกลมยกขึ้น
        ตอนถูกเลือก = แคปซูลทึบ (เป็นช่องเดียวที่เปลี่ยนรูป ไม่ใช่แค่เปลี่ยนสีอักษร)
```

**ชื่อช่องคือ `KeviN`** — อีกสี่ช่องเป็น*สถานที่* ส่วนช่องนี้เป็น*ใครสักคน* ป้ายจึงควรเป็นชื่อไม่ใช่คำกริยา
· ผลพลอยได้คือเป็นช่องเดียวที่เป็นอักษรละตินท่ามกลางป้ายไทย แยกออกทันทีโดยไม่ต้องเพิ่มสีหรือรูปทรงใหม่
· **หัวจอในหน้านั้นต้องเป็น `KeviN` ด้วย** ป้ายกับหัวหน้าที่ไม่ตรงกันทำให้ไม่แน่ใจว่ากดถูกที่ไหม

> ⚠️ ห้าช่องบนจอ 360px ได้ช่องละราว 66px · **ต้องวัดบนเครื่องจริง** ป้ายที่เสี่ยงตกบรรทัดคือ “ตั้งค่า” ไม่ใช่ `KeviN`

### หน้า KeviN

ตัวสลับโหมดเป็น segmented control บนสุด — **แชต | โทร**

**โหมดโทรต้องมีสถานะนิ่งเป็นค่าตั้งต้นเสมอ** เปิดไมค์เองทันทีที่เข้าหน้าทำไม่ได้
ทั้งเพราะเจ้าของสั่งไว้ และเพราะกดพลาดแล้วเสียงในห้องเรียนวิ่งไปถึง Google ทันที

| สถานะ | บนจอ |
|---|---|
| ยังไม่เริ่ม | ไอคอนไมค์**สีเทา** · “พร้อมคุยแล้ว / ไมค์ยังปิดอยู่” · ปุ่ม **เริ่มโทร** เป็นม่วงก้อนเดียวในหน้า |
| กำลังฟัง | วงคลื่นสีฟ้า · **ไม่มีคำบรรยายฝั่งเรา** · ปุ่ม ปิดไมค์ / วางสาย / เลือกไมค์ |
| กำลังตอบ | วงคลื่นสีม่วง · คำบรรยายคำตอบ · แถบเล็กบอกว่ากำลังอ่าน tool อะไร |
| แชตว่าง | ตัวอย่างคำถามสามอันที่ระบบตอบได้ดีจริง — สอนขอบเขตโดยไม่ต้องเขียนว่าทำอะไรไม่ได้ |
| ขอสิ่งที่ทำไม่ได้ | ปฏิเสธหนึ่งบรรทัด + การ์ด **เปิดหน้างานนี้เพื่อแก้** |
| ต่อจากสาย | แถบฟ้า “↩ ต่อจากสายเมื่อ N นาทีที่แล้ว” |

**คำบรรยายขึ้นตลอดสาย เฉพาะฝั่ง KeviN** — ได้ transcript มาฟรีอยู่แล้ว
และหูฟังคำว่า “E 17501” พลาดง่ายกว่าตาอ่านมาก

**ฝั่งเราไม่ขึ้นเลย** (เจ้าของสั่ง 1 ก.ย. 2026) — เห็นคำที่ตัวเองเพิ่งพูดวิ่งขึ้นจอไม่ได้ช่วยอะไร
และถ้าถอดเสียงผิดจะอ่านว่าระบบฟังผิดทั้งที่มันฟังถูก
ผลพลอยได้คือ **ฝั่งเบราว์เซอร์ไม่ถือข้อความที่ผู้ใช้พูดไว้ในหน่วยความจำเลย** เหลือแค่ธงว่าพูดแล้ว
เพื่อลงแถว `- voice -` ให้ครบจังหวะ · คำตอบล่าสุดของ KeviN ค้างไว้ตอนเราพูด เพราะยังอยากอ่านมันอยู่

### ความสูงของหน้า — รากของสองอาการ

`.talk` ต้องสูง **เต็มจอ** (`100dvh` ลบขอบของ `.wrap`) ไม่ใช่ `min-height: 60vh`

ถ้ากล่องเตี้ย โหมดโทรจะจัดกลางของ*กล่องเตี้ย* ไม่ใช่กลางจอ (ดูลอยไปข้างบน)

`.thread` เลื่อนในตัวเอง (`flex:1` + `min-height:0` + `overflow-y:auto`)
หัวข้อกับแท็บจึงไม่เลื่อนหายตอนแชตยาว

**ช่องพิมพ์เป็น `fixed` ลอยอยู่เหนือแถบล่าง** ไม่ใช่แถวล่างสุดของ `.talk` แล้ว
(เปลี่ยน 1 ก.ย. 2026 ให้เข้าชุดกับปุ่มเพิ่มเร็วที่ลอยอยู่ในหน้าอื่น) — สามข้อที่ผูกกัน:

- ระยะเผื่อให้มันต้องอยู่ที่ **`padding-bottom` ของ `.talk`** ไม่ใช่ของ `.thread`
  ใส่ที่ตัวเลื่อนเมื่อไหร่ แถบเลื่อนจะยาวลงไปใต้ช่องพิมพ์แล้วดูเหมือนจมหาย
- `.composer` **ไม่มีพื้นรองและไม่มี padding** — `.thread` จางตัวเองด้วย `mask-image`
  ข้อความจึงหายไปก่อนถึงช่องพิมพ์อยู่แล้ว · พื้นทึบที่เคยมีกลบแสงพื้นจนเห็นเป็นแถบด้าน
- เดสก์ท็อปเนื้อหา**ชิดซ้ายหลังแถบข้าง 200px ไม่ได้อยู่กลางจอ** ช่องพิมพ์จึงอ้างอิง
  ขอบซ้ายของ `.wrap` ตรง ๆ ไม่ใช่ `left: 50%`

> ⚠️ **`dvh` ไม่ใช่ `vh`** — บนมือถือ `vh` ไม่หดตามแถบเบราว์เซอร์และคีย์บอร์ด
> พอคีย์บอร์ดเด้งขึ้นมา ช่องพิมพ์จะถูกดันไปอยู่ใต้คีย์บอร์ด

### ไม่มีสีใหม่ ฟอนต์ใหม่ หรือรูปทรงใหม่เข้าระบบ

```sql
tool_calls    (id, message_id, user_id, name, input jsonb, output jsonb, status, created_at)
```

RLS ครบทุกตารางเหมือนของเดิม · **สองโหมดเขียนลงบทสนทนาเดียวกัน** จึงได้ของแถมที่คุ้มมาก —
**วางสายแล้วเปิดแชตพิมพ์ต่อได้เลยโดยมันจำว่าเมื่อกี้คุยอะไร** เกือบไม่ต้องเขียนอะไรเพิ่ม

## 10 · เมื่อของพัง

| อาการ | ผู้ใช้เห็นอะไร | ทางถอย |
|---|---|---|
| โควตาเสียงหมด | เปิดสายไม่ได้ | สลับไปโหมดแชต — คนละโควตา |
| สายครบ 15 นาที | **ไม่เห็นอะไรเลย** | ต่อด้วย resumption handle |
| เน็ตหลุดกลางสาย | เสียงเงียบไปครู่หนึ่ง | handle เดิม ต่อได้เลย |
| token หมดอายุ | ต่อสายใหม่ไม่ติด | ขอใบใหม่ที่ `/api/voice/token` |
| **tool ล่ม** | **โมเดลบอกว่าดึงข้อมูลไม่ได้** | คืน error ให้โมเดล **ห้ามคืนค่าว่างเงียบ ๆ** |
| ไมค์ถูกปฏิเสธ | ปุ่มโทรกดไม่ได้ | บอกวิธีเปิดสิทธิ์ แบบเดียวกับหน้า `/settings` |

**แถวที่สำคัญที่สุดคือ `tool ล่ม`** — ถ้าคืนรายการว่างแทน error โมเดลจะพูดอย่างมั่นใจว่า
“พรุ่งนี้ไม่ติดอะไรเลย” ทั้งที่แค่ query ไม่ผ่าน ซึ่งผิดหลัก UX ข้อ 5 ตรง ๆ
และเป็นคำโกหกที่แพงที่สุดที่แอปนี้พูดได้

## 11 · กับดักที่รู้ล่วงหน้า

| เรื่อง | ต้องระวัง |
|---|---|
| **iOS** | `SpeechRecognition` ใช้ไม่ได้ใน PWA ที่ติดตั้งบน iOS · ตอนนี้ไม่กระทบเพราะใช้ Android แต่ถ้าเปลี่ยนเครื่องต้องรื้อโหมดสำรอง |
| prompt สองที่เพี้ยนจากกัน | ต้นฉบับต้องมีไฟล์เดียว (`CLAUDE-PROJECT-PROMPT.md`) แล้ว build เข้าทั้งประตู MCP และประตูแอป · ถ้าก๊อปวางด้วยมือ สองประตูจะมีนิสัยต่างกันภายในเดือนเดียว |
| บุคลิกไม่ตรงกันสองโหมด | เสียงเป็นเพื่อนแต่แชตพูดเหมือนคู่มือ = รู้สึกเหมือนคนละคน · prompt เดียวกันทั้งสองช่องทาง |
| tool แก้กลางสายไม่ได้ | Live API ล็อกชุด tool ตอนเปิด session · เพิ่ม tool ต้องวางสายแล้วต่อใหม่ |
| ephemeral token | ผูก config ตายกับ token ตอนสร้าง คนขโมยไปสั่ง prompt อื่นไม่ได้ · และจำกัดจำนวน session/วัน/คน |
| `AudioContext` | ต้องเริ่มจาก user gesture ไม่งั้นเบราว์เซอร์เมินเงียบ ๆ — อีกเหตุผลที่ต้องมีปุ่ม “เริ่มโทร” |

## 12 · ลำดับการทำ

ดู [`PLAN.md`](../PLAN.md) หัวข้อ **“ประตูที่สาม”** สำหรับเกณฑ์เสร็จของแต่ละขั้น

| | ทำอะไร | สถานะ |
|---|---|---|
| **0** | ฟังเสียง Live API ภาษาไทยใน AI Studio | ✅ ผ่าน |
| 1 | ชั้น tool อ่านอย่างเดียว + ตัวกรอง Area + ด่านกันเขียน | ✅ |
| 2 | หน้าแชตข้อความ + ช่อง `KeviN` ในแถบล่าง | ✅ ใช้งานจริงแล้ว |
| 3 | endpoint แจก token + ต่อสาย + ต่อสายอัตโนมัติ | ✅ **ยกเว้นขาไมค์ที่ยังไม่ได้ทดสอบ** |
| 4 | ประวัติร่วมกัน + สถานะพิเศษที่เหลือ | ✅ |

**ขั้น 0 มาก่อนทุกอย่าง** เพราะตอบคำถามที่เหลือทั้งหมดโดยไม่ต้องลงแรง
**ขั้น 2 ส่งมอบคุณค่าได้ด้วยตัวเอง** ถ้าเสียงไปต่อไม่ได้ ก็ยังได้แชตบนมือถือไปแล้ว
