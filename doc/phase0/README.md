## ขั้นที่ 7 · ใส่วิชาและตารางเรียน

วาง [`04-seed-timetable.sql`](04-seed-timetable.sql) → Run — **กรอกตารางจริงไว้ให้แล้ว ไม่ต้องแก้อะไร**

8 วิชา 11 คาบ อิงตามปฏิทินการศึกษา ป.ตรี มก. ปีการศึกษา 2569 ภาคต้น

| ค่า | ที่มา |
|---|---|
| `term_start` = **2026-08-03** | First Day of Classes · เป็นวันจันทร์พอดี |
| `weeks` = **17** | คลุมถึง Last day of classes ภาคพิเศษ 29 พ.ย. 2026 |

ตรวจสอดคล้องแล้ว: สัปดาห์ของวันที่ 17 ส.ค. = offset 2 = **สัปดาห์ที่ 3** ตรงกับที่เจ้าของยืนยัน

ผลที่ทดสอบในเครื่อง:

| ตรวจ | ผล |
|---|---|
| วิชา / คาบ / occurrence | 8 · 11 · **187** (11 × 17) |
| คาบแรก | 2026-08-03 ตรง First Day of Classes พอดี |
| คาบสุดท้าย | 2026-11-27 — ไม่เกิน 29 พ.ย. |
| ทุกคาบลงวันตรงที่ประกาศ | ผ่านทั้ง 187 |
| คาบชนกันเอง | ไม่มี |

> 📌 **สัปดาห์สอบกลางภาค 19–27 ก.ย.** ตรงกับ week_offset 7 (21–27 ก.ย.) ซึ่งตอนนี้มีคาบอยู่ 11 คาบ
> ปฏิทินไม่ได้ประกาศงดคาบ จึงใส่ครบไว้ก่อน ถ้าจริง ๆ ไม่มีเรียน ตัดออกได้ด้วยคำสั่งท้ายไฟล์
> หรือค่อยติ๊กออกทีหลังในหน้า S6 (เฟส 3)

ของแถมสำหรับเฟส 3 — แกนเวลาของปฏิทินสัปดาห์คือ **08:00–20:30**
(เร็วสุด 09:00 − 1 ชม. ถึงช้าสุด 19:30 + 1 ชม.) ตามกฎใน TRAPS.md

## บั๊กที่เจอตอนทดสอบ (แก้ใน `SCHEMA.sql` แล้ว)

ทั้งสามข้อ *ไม่* ใช่การเปลี่ยนสิ่งที่ตัดสินใจไว้ — เป็นกรณีที่โค้ดทำไม่ได้อย่างที่ชื่อตัวเองบอก
เจตนาเดิมใน DECISIONS.md ยังอยู่ครบ

### 1 · `sched_weeks_present` ไม่ได้กันอะไรเลย

```sql
check (array_length(week_offsets, 1) >= 1)     -- เดิม
```

`array_length('{}', 1)` คืน **NULL ไม่ใช่ 0** และ CHECK ที่ได้ผลเป็น NULL ถือว่า "ผ่าน" ใน Postgres
ด่านนี้จึงปล่อยอาเรย์ว่างเข้ามาได้ → คาบนั้นไม่โผล่ในปฏิทินสักสัปดาห์ **โดยไม่มี error อะไรเลย**

```sql
check (coalesce(array_length(week_offsets, 1), 0) >= 1)   -- แก้แล้ว
```

### 2 · `sched_weeks_valid` ปล่อย NULL ผ่าน

```sql
check (0 <= all(week_offsets))                 -- เดิม
```

`0 <= all('{0,NULL}')` คืน NULL → ผ่านอีกเหมือนกัน
สัปดาห์ที่เป็น NULL จะถูก `between` ใน `schedule_occurrences()` กรองทิ้งเงียบ ๆ — คาบหายไปโดยไม่มีสัญญาณ

```sql
check (array_position(week_offsets, null) is null and 0 <= all(week_offsets))   -- แก้แล้ว
```

> ทั้งสองข้อขัดกับหลักการ UX ข้อ 5 ตรง ๆ — "ไม่มีอะไรหายเงียบ ๆ"

### 3 · ใครก็ได้บนอินเทอร์เน็ตเรียก `claim_due_reminders()` ได้

ข้อนี้หนักสุด ฟังก์ชันเป็น `security definer` จึง**ข้าม RLS** และ Postgres เปิดให้ `PUBLIC` เรียกได้เป็นค่าเริ่มต้น
`anon key` อยู่ใน bundle ฝั่งเบราว์เซอร์ ใครเปิด DevTools ก็เห็น แล้วยิง
`POST /rest/v1/rpc/claim_due_reminders` ได้เลย ผลคือ

1. **อ่าน reminder ทุกแถว** — หัวข้อและเนื้อหาทั้งหมด แม้ RLS จะกันการอ่านตรง ๆ ไว้แล้ว
2. **เซ็ต `notified_at` ทิ้ง** → cron ตัวจริงไม่เจอแถว → **push ไม่เด้ง** และไม่มี error ให้เห็น

ทดสอบยืนยันแล้วว่าเกิดขึ้นจริง และหลังแก้ `anon` กับ `authenticated` โดนปฏิเสธ ส่วน `service_role`
ที่ Edge Function ใช้ยังเรียกได้ปกติ

```sql
revoke all on function public.claim_due_reminders() from public, anon, authenticated;
grant execute on function public.claim_due_reminders() to service_role;
```

## หมายเหตุสำหรับคนที่จะทดสอบซ้ำในเครื่อง

psql บน Windows ภาษาไทยจะตั้ง `client_encoding` เป็น **WIN874** แล้วอ่านคอมเมนต์ไทยใน
`SCHEMA.sql` (ซึ่งเป็น UTF-8) พังกลางไฟล์ ตั้ง `PGCLIENTENCODING=UTF8` ก่อนรันเสมอ

เรื่องนี้เกิดเฉพาะ psql ในเครื่อง — **SQL Editor ของ Supabase เป็น UTF-8 อยู่แล้ว ไม่เจอปัญหานี้**
