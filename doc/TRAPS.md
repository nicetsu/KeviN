# TRAPS — กับดักที่รู้ล่วงหน้า

อ่านหัวข้อที่เกี่ยวก่อนเขียนโค้ดส่วนนั้น ทุกข้อในนี้เคยทำให้โปรเจกต์อื่นเสียเวลามาแล้ว

---

## ความปลอดภัย

### `service_role` key ห้ามหลุดไปฝั่งเบราว์เซอร์
กุญแจนี้ข้าม RLS ได้ทั้งหมด ให้อยู่แค่ใน Edge Function เท่านั้น
ฝั่ง Next.js ใช้ `anon key` คู่กับ RLS · ตัวแปรที่ขึ้นต้น `NEXT_PUBLIC_` ทุกตัวไปอยู่ใน bundle ที่ผู้ใช้เปิดดูได้

### ถ้าทำแชตในแอปเอง — API key ห้ามอยู่ฝั่ง PWA
ต้องผ่าน Edge Function เสมอ · ใครก็เปิดดูโค้ดฝั่งเบราว์เซอร์ได้ แล้วเอาคีย์ไปใช้จนบิลบาน

### MCP ให้สิทธิ์รัน SQL ดิบ
Supabase เองแนะนำให้ใช้ MCP กับข้อมูลที่ไม่ใช่ production แต่เคสเรากลับกัน — ข้อมูลนี้คือของจริงและต้องเขียนได้
ทางลดความเสี่ยงที่ต้องทำครบทั้งสี่: `project_ref` + `features=database,docs` · CHECK constraint + RLS · prompt บังคับยืนยันก่อนเขียน · ใช้ `archived_at` แทน `DELETE`

## การแจ้งเตือน

### iOS ต้องติดตั้งลงหน้าจอโฮมก่อนถึงจะรับ push ได้
Safari บน iPhone ไม่ให้เว็บทั่วไปส่ง push — ต้องกดปุ่มแชร์ → "เพิ่มลงหน้าจอโฮม" → เปิดจากไอคอน → แล้วค่อยขอสิทธิ์
**ถ้าไม่ทำหน้าจอสอนขั้นตอนนี้ไว้ จะกลายเป็นบั๊กที่หาสาเหตุไม่เจอในอีกสามเดือน**
ให้แสดงคำแนะนำเฉพาะเมื่อตรวจพบว่าเปิดจาก Safari บน iOS และยังไม่ได้ติดตั้ง — ไม่งั้นรกหน้าจอคนใช้ Android

### VAPID key เปลี่ยนไม่ได้
สร้างคู่กุญแจครั้งเดียวแล้วเก็บให้ดี · ถ้า regenerate ใหม่ subscription เก่าทั้งหมดตายทันที ทุกเครื่องต้องกดอนุญาตใหม่หมด

### push ซ้ำเพราะ cron รอบทับกัน
cron รันทุกนาที ถ้ารอบก่อนยังไม่จบจะยิงซ้ำ
ต้องเขียน `notified_at` **ในคำสั่งเดียวกับที่เลือกแถว** — ใช้ `claim_due_reminders()` ที่มีใน SCHEMA.sql แล้ว
**ห้ามแยกเป็น `SELECT` แล้วค่อย `UPDATE`** ต่อให้อยู่ใน transaction เดียวกัน

### Vercel Cron แพลนฟรีรันได้วันละครั้ง
เตือน "อีก 30 นาทีมี quiz" ไม่ได้ · นี่คือเหตุผลที่เลือก pg_cron ตั้งแต่แรก อย่าเผลอย้ายกลับ

## Supabase จากฝั่งเซิร์ฟเวอร์

### `update()` หลายคำสั่งพร้อมกันต้องมี `.select()` ไม่งั้นไม่เขียน
`reorderItems` ยิง `supabase.from('items').update(...)` หลายตัวพร้อมกันผ่าน `Promise.all`
**ไม่มี error ไม่มี rowcount และไม่มีแถวไหนถูกเขียนเลย** ลากแล้วดูเหมือนได้ กด F5 ทีลำดับเด้งกลับหมด
ใส่ `.select('id')` ต่อท้ายแล้วเขียนติดครบทันที

สังเกตว่า `toggleDone`/`archiveItem` ที่ยิงคำสั่งเดียวไม่มี `.select()` เขียนติดปกติ (ตรวจจาก
`updated_at` ในข้อมูลจริงแล้ว) — กลไกที่แท้จริงยังไม่ได้พิสูจน์ รู้แค่ว่าเงื่อนไขนี้ทำให้พัง

**กฎที่ใช้ไปก่อน:** เขียนข้อมูลเมื่อไหร่ให้ `.select()` แล้วเช็กจำนวนแถวที่ได้กลับมาทุกครั้ง
`update` ที่ไม่โดนสักแถวถือว่า "สำเร็จ" ในสายตา PostgREST — ถ้าไม่นับแถวเอง จะไม่มีวันรู้ว่าพัง

## เวลา

### เก็บ UTC เสมอ — ยกเว้นที่เดียว
ใช้ `timestamptz` ตลอด แล้วแปลงเป็น Asia/Bangkok ตอนแสดงผล
**ยกเว้น `project_schedules.start_time` / `end_time` ที่ต้องเป็น `time` เปล่า** เพราะ "09:00 ทุกวันจันทร์" คือเวลาท้องถิ่น ไม่ใช่จุดเวลาจุดเดียว

### `start_date` ต้องเป็นวันจันทร์เสมอ
มี CHECK constraint บังคับไว้แล้ว · ตอนคำนวณจากอินพุตผู้ใช้ ต้องปัดลงไปหาวันจันทร์ของสัปดาห์นั้นก่อน ไม่งั้น insert ไม่ผ่าน

## ปฏิทิน

### แกนของปฏิทินสัปดาห์กลับด้านจากที่คุ้นเคย
**วัน = แกนตั้ง · เวลา = แกนนอน** ไม่ใช่แบบ Google Calendar
วางบล็อกด้วย `grid-row: <วันในสัปดาห์>` และ `grid-column: <เวลาเริ่ม> / span <จำนวนชั่วโมง>`
โค้ดตัวอย่างที่ทำงานได้จริงอยู่ใน `ui-kit.html` (ส่วน `.wk`)

### บล็อกที่เวลาซ้อนกัน
ในแกนแบบนี้ ถ้าสองคาบชนกันต้อง**แบ่งความสูงในแถวของวันนั้น** ไม่ใช่แบ่งความกว้าง
ต้องมีตรรกะรองรับตั้งแต่ตอนเขียน ไม่งั้นบล็อกจะทับกันจนอ่านไม่ได้

### แกนเวลาอย่า fix 00:00–24:00
คำนวณจากข้อมูลจริง — คาบเร็วสุดลบ 1 ชม. ถึงช้าสุดบวก 1 ชม.

## Claude / prompt

### Claude ลบของโดยไม่ได้ตั้งใจ
prompt ต้องกำหนดชัดว่าการลบถามยืนยันทุกครั้ง และเสนอ `archived_at` แทน

### ถ้าใช้ Anthropic API เอง — ห้ามปิด thinking บน Opus 5
เมื่อ `thinking: {type: "disabled"}` โมเดลจะเขียนคำสั่งเรียก tool ออกมาเป็น**ข้อความธรรมดา**เป็นบางครั้ง แทนที่จะเรียก tool จริง
ผลคือบทสนทนาจบสวยงามแต่**งานไม่ถูกบันทึกลง DB** ไม่มี error ไม่มีสัญญาณอะไรเลย
เคสของเราเป็น tool call ล้วน ๆ จึงเจอเต็ม ๆ — **ให้เปิด thinking ไว้แล้วลด `effort` เป็น `low`/`medium` แทน** ประหยัดพอกันและไม่พัง

### Opus 5 ขยายขอบเขตงานเอง
มีแนวโน้มเพิ่มขั้นตอนที่ไม่ได้ขอ · ถ้าเจอ ให้ใส่คำสั่งจำกัดขอบเขตใน prompt แทนการแก้ทีละครั้ง
