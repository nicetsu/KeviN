# TRAPS — กับดักที่รู้ล่วงหน้า

อ่านหัวข้อที่เกี่ยวก่อนเขียนโค้ดส่วนนั้น ทุกข้อในนี้เคยทำให้โปรเจกต์อื่นเสียเวลามาแล้ว

---

## ความปลอดภัย

### `service_role` key ห้ามหลุดไปฝั่งเบราว์เซอร์
กุญแจนี้ข้าม RLS ได้ทั้งหมด ให้อยู่แค่ใน Edge Function เท่านั้น
ฝั่ง Next.js ใช้ `anon key` คู่กับ RLS · ตัวแปรที่ขึ้นต้น `NEXT_PUBLIC_` ทุกตัวไปอยู่ใน bundle ที่ผู้ใช้เปิดดูได้

### ถ้าทำแชตในแอปเอง — API key ห้ามอยู่ฝั่ง PWA
ต้องผ่าน Edge Function เสมอ · ใครก็เปิดดูโค้ดฝั่งเบราว์เซอร์ได้ แล้วเอาคีย์ไปใช้จนบิลบาน

### MCP ให้สิทธิ์รัน SQL ดิบ
Supabase เองแนะนำให้ใช้ MCP กับข้อมูลที่ไม่ใช่ production แต่เคสเรากลับกัน — ข้อมูลนี้คือของจริงและต้องเขียนได้
ทางลดความเสี่ยงที่ต้องทำครบทั้งสี่: `project_ref` + `features=database,docs` · CHECK constraint + RLS · prompt บังคับยืนยันก่อนเขียน · ใช้ `archived_at` แทน `DELETE`

## การแจ้งเตือน

### iOS ต้องติดตั้งลงหน้าจอโฮมก่อนถึงจะรับ push ได้
Safari บน iPhone ไม่ให้เว็บทั่วไปส่ง push — ต้องกดปุ่มแชร์ → "เพิ่มลงหน้าจอโฮม" → เปิดจากไอคอน → แล้วค่อยขอสิทธิ์
**ถ้าไม่ทำหน้าจอสอนขั้นตอนนี้ไว้ จะกลายเป็นบั๊กที่หาสาเหตุไม่เจอในอีกสามเดือน**
ให้แสดงคำแนะนำเฉพาะเมื่อตรวจพบว่าเปิดจาก Safari บน iOS และยังไม่ได้ติดตั้ง — ไม่งั้นรกหน้าจอคนใช้ Android

### VAPID key เปลี่ยนไม่ได้
สร้างคู่กุญแจครั้งเดียวแล้วเก็บให้ดี · ถ้า regenerate ใหม่ subscription เก่าทั้งหมดตายทันที ทุกเครื่องต้องกดอนุญาตใหม่หมด

### push ซ้ำเพราะ cron รอบทับกัน
cron รันทุกนาที ถ้ารอบก่อนยังไม่จบจะยิงซ้ำ
ต้องเขียน `notified_at` **ในคำสั่งเดียวกับที่เลือกแถว** — ใช้ `claim_due_reminders()` ที่มีใน SCHEMA.sql แล้ว
**ห้ามแยกเป็น `SELECT` แล้วค่อย `UPDATE`** ต่อให้อยู่ใน transaction เดียวกัน

### Vercel Cron แพลนฟรีรันได้วันละครั้ง
เตือน "อีก 30 นาทีมี quiz" ไม่ได้ · นี่คือเหตุผลที่เลือก pg_cron ตั้งแต่แรก อย่าเผลอย้ายกลับ

## ความเร็ว

### Vercel ไม่ได้เดา region ให้ — ค่าเริ่มต้นคือเวอร์จิเนีย
ไม่มี `vercel.json` = ฟังก์ชันไปรันที่ `iad1` ไม่ว่าผู้ใช้กับฐานข้อมูลจะอยู่ไหน
เคสเรา ผู้ใช้อยู่ไทย DB อยู่โตเกียว แต่ฟังก์ชันอยู่สหรัฐฯ ทุก query จึงข้ามแปซิฟิกไปกลับ
ดูได้จาก header `X-Vercel-Id` — `sin1::iad1` แปลว่าเข้า edge สิงคโปร์ แต่รันที่เวอร์จิเนีย

**ให้ฟังก์ชันอยู่ region เดียวกับฐานข้อมูล ไม่ใช่ใกล้ผู้ใช้** — หนึ่งหน้ามี query หลายรอบ
แต่ขาเบราว์เซอร์มีรอบเดียว

### `next build` ทับ dev server ที่รันอยู่ แล้วเสิร์ฟของค้างเงียบ ๆ
`next dev` กับ `next build` ใช้โฟลเดอร์ `.next` ร่วมกัน · ถ้ารัน build ตอนที่ dev server ยังรันอยู่
production build จะเขียนทับไฟล์ที่ dev server กำลังเสิร์ฟ แล้ว dev server เสิร์ฟของครึ่ง ๆ กลาง ๆ ต่อไป
**ไม่มี error ไม่มีคำเตือน** — หน้าเว็บขึ้น 200 ปกติ แต่เป็นโค้ดหรือ CSS ของรอบก่อน

เคยทำให้ตามหาบั๊กสีในปฏิทินอยู่นาน ทั้งที่โค้ดถูกมาตั้งแต่แรก
เบาะแสคือ **ข้อความบนจอเป็นของเวอร์ชันกลางทาง** ที่ไม่มีอยู่ในไฟล์แล้ว

**ถ้าจะรัน build ให้ปิด dev server ก่อน** และถ้าเจออาการแปลก ๆ ให้ `rm -rf web/.next` แล้วเปิดใหม่
· ฝั่งเบราว์เซอร์ต้องกด Ctrl+Shift+R ด้วย เพราะ CSS เก่าค้างในแคชได้
· CSS เก่าที่ไม่มี custom property ตัวใหม่จะทำให้ `var(--x)` หาค่าไม่เจอ แล้วสีกลายเป็นใส มองไม่เห็น

### `getUser()` ยิงเน็ตทุกครั้ง
ชื่อฟังก์ชันชวนให้คิดว่าอ่านจาก cookie แต่มันถามเซิร์ฟเวอร์ Supabase จริงทุกครั้ง
ถ้าเรียกทั้งใน proxy และใน action = จ่ายสองรอบต่อการกดหนึ่งครั้ง
ในเว็บนี้ `proxy.ts` ยืนยันให้แล้วทุก request จึงเหลือใช้ `getClaims()` (ตรวจในเครื่อง) ที่ action

## Supabase จากฝั่งเซิร์ฟเวอร์

### `update()` หลายคำสั่งพร้อมกันต้องมี `.select()` ไม่งั้นไม่เขียน
`reorderItems` ยิง `supabase.from('items').update(...)` หลายตัวพร้อมกันผ่าน `Promise.all`
**ไม่มี error ไม่มี rowcount และไม่มีแถวไหนถูกเขียนเลย** ลากแล้วดูเหมือนได้ กด F5 ทีลำดับเด้งกลับหมด
ใส่ `.select('id')` ต่อท้ายแล้วเขียนติดครบทันที

สังเกตว่า `toggleDone`/`archiveItem` ที่ยิงคำสั่งเดียวไม่มี `.select()` เขียนติดปกติ (ตรวจจาก
`updated_at` ในข้อมูลจริงแล้ว) — กลไกที่แท้จริงยังไม่ได้พิสูจน์ รู้แค่ว่าเงื่อนไขนี้ทำให้พัง

**กฎที่ใช้ไปก่อน:** เขียนข้อมูลเมื่อไหร่ให้ `.select()` แล้วเช็กจำนวนแถวที่ได้กลับมาทุกครั้ง
`update` ที่ไม่โดนสักแถวถือว่า "สำเร็จ" ในสายตา PostgREST — ถ้าไม่นับแถวเอง จะไม่มีวันรู้ว่าพัง

## กิจกรรม (events)

### `week_offsets` ไม่ใช่ที่เก็บ "ฉันจะไม่ไป"
`week_offsets` แปลว่า **สัปดาห์นั้นไม่มีคาบ** (มหาลัยหยุด · สัปดาห์สอบ · Commencement Week)
การเอาไปใช้แทนความหมาย "คาบมีอยู่แต่ไม่ไป" ให้ผลบนปฏิทินที่หน้าตาถูกต้องเป๊ะ **แต่ทำลายข้อมูลถาวร**

- ย้อนดูแล้วแยกไม่ออกว่าวันนั้นหยุดจริงหรือโดดเรียน
- วิชาที่มีหลายคาบในสัปดาห์เดียว (บรรยาย + แล็บ) จะหายทั้งหมด ไม่ใช่คาบเดียว
- เลิกทำไม่ได้ เพราะไม่มีอะไรบันทึกว่าเลขสัปดาห์ไหนถูกลบ

ตอนนี้**ยังไม่มีที่เก็บ**ความหมายนี้ · `doc/CLAUDE-PROJECT-PROMPT.md` มีกติกาห้าม Claude แตะไว้แล้ว
จะมาพร้อมตาราง `time_offsets` ในงานรอบถัดไป

### `on delete set null` บน FK สองคอลัมน์ ต้องระบุคอลัมน์
`items.event_id` อ้าง `events(id, project_id)` เพื่อให้ Postgres บังคับเองว่างานกับ event อยู่ project เดียวกัน
ถ้าเขียน `on delete set null` เปล่า ๆ **Postgres จะพยายามเซ็ต `project_id` เป็น null ด้วย** ซึ่งชน NOT NULL แล้วการลบ event จะล้มทั้งคำสั่ง
ต้องเขียน `on delete set null (event_id)` ระบุคอลัมน์ไว้ (ต้องการ Postgres 15 ขึ้นไป · ของจริงรัน 17.6)

### CHECK ใส่ `at time zone` ไม่ได้
Postgres รับเฉพาะฟังก์ชัน IMMUTABLE ใน CHECK แต่ `timestamptz at time zone 'Asia/Bangkok'` เป็น **STABLE**
กฎแบบ "ห้าม event ข้ามเที่ยงคืน" หรือ "กำหนดการต้องอยู่ในช่วงของงาน" จึงบังคับที่ DB ไม่ได้ตรง ๆ
ที่ทำได้คือเงื่อนไขที่เป็นเลขคณิตล้วน เช่น `ends_at <= starts_at + interval '30 days'`

### `"24:00:00"` ประกอบเป็น `Date` ไม่ได้
`calendar_entries()` ให้บล็อกที่วิ่งชนเที่ยงคืนมาเป็น `end_time = '24:00:00'`
`new Date('2026-09-05T24:00:00+07:00')` คืน **Invalid Date** เงียบ ๆ ไม่ throw
ต้องแปลงเป็นเที่ยงคืนของวันถัดไปเอง — ทำไว้แล้วใน `entryEndMs()` ที่ `web/lib/calendar.ts` **ห้ามคำนวณเองที่อื่น**

### คีย์ของบล็อกปฏิทินต้องมีวันที่ด้วย
`source_id` อย่างเดียวไม่พอสองชั้น — คาบเรียนใบเดียวโผล่ทุกสัปดาห์ และ event ข้ามคืนใบเดียวถูกหั่นเป็นหลายบล็อกที่ใช้ id เดียวกัน
ใช้ `entryKey()` ที่รวม `kind` + `source_id` + `occurs_on`

### `shape()` ที่ใส่ `event_id: null` ทุกครั้ง = ปลดการผูกเงียบ ๆ
แผงแก้ไข (S7) สร้าง `ItemDraft` โดยไม่รู้จัก event เลย
ถ้า `shape()` ใส่ `event_id: null` ลงไปเสมอ การกดแก้ชื่องานเฉย ๆ จะปลดงานออกจากกิจกรรมโดยไม่มีอะไรเตือน
กฎคือ **ละคีย์ไว้ = ไม่แตะ · ใส่ `null` = ปลด** (ดู `web/app/actions/items.ts`)

### เปิดหน้าแก้แล้วกดบันทึก เวลาที่อนุมานจะกลายเป็นเวลาที่กรอกเอง
`event_agenda.end_time` ที่เป็น null ถูกเติมค่าตอน**แสดงผล** ไม่ใช่ตอนเก็บ
หน้าแก้ต้องคืนช่องเวลาจบให้เป็นช่องว่างเมื่อ DB เก็บ null ไว้ ไม่ใช่เอาค่าที่เติมแล้วมาใส่
ไม่งั้นแค่เปิดหน้าแก้แล้วกดบันทึก ข้อมูลที่เคยยืดหยุ่นจะถูกตรึงถาวร

## เวลา

### เก็บ UTC เสมอ — ยกเว้นที่เดียว
ใช้ `timestamptz` ตลอด แล้วแปลงเป็น Asia/Bangkok ตอนแสดงผล
**ยกเว้น `project_schedules.start_time` / `end_time` ที่ต้องเป็น `time` เปล่า** เพราะ "09:00 ทุกวันจันทร์" คือเวลาท้องถิ่น ไม่ใช่จุดเวลาจุดเดียว

### `start_date` ต้องเป็นวันจันทร์เสมอ
มี CHECK constraint บังคับไว้แล้ว · ตอนคำนวณจากอินพุตผู้ใช้ ต้องปัดลงไปหาวันจันทร์ของสัปดาห์นั้นก่อน ไม่งั้น insert ไม่ผ่าน

## ปฏิทิน

### แกนของปฏิทินสัปดาห์กลับด้านจากที่คุ้นเคย
**วัน = แกนตั้ง · เวลา = แกนนอน** ไม่ใช่แบบ Google Calendar
วางบล็อกด้วย `grid-row: <วันในสัปดาห์>` และ `grid-column: <เวลาเริ่ม> / span <จำนวนชั่วโมง>`
โค้ดตัวอย่างที่ทำงานได้จริงอยู่ใน `ui-kit.html` (ส่วน `.wk`)

### บล็อกที่เวลาซ้อนกัน
ในแกนแบบนี้ ถ้าสองคาบชนกันต้อง**แบ่งความสูงในแถวของวันนั้น** ไม่ใช่แบ่งความกว้าง
ต้องมีตรรกะรองรับตั้งแต่ตอนเขียน ไม่งั้นบล็อกจะทับกันจนอ่านไม่ได้

### แกนเวลาอย่า fix 00:00–24:00
คำนวณจากข้อมูลจริง — คาบเร็วสุดลบ 1 ชม. ถึงช้าสุดบวก 1 ชม.

## Claude / prompt

### Claude ลบของโดยไม่ได้ตั้งใจ
prompt ต้องกำหนดชัดว่าการลบถามยืนยันทุกครั้ง และเสนอ `archived_at` แทน

### ถ้าใช้ Anthropic API เอง — ห้ามปิด thinking บน Opus 5
เมื่อ `thinking: {type: "disabled"}` โมเดลจะเขียนคำสั่งเรียก tool ออกมาเป็น**ข้อความธรรมดา**เป็นบางครั้ง แทนที่จะเรียก tool จริง
ผลคือบทสนทนาจบสวยงามแต่**งานไม่ถูกบันทึกลง DB** ไม่มี error ไม่มีสัญญาณอะไรเลย
เคสของเราเป็น tool call ล้วน ๆ จึงเจอเต็ม ๆ — **ให้เปิด thinking ไว้แล้วลด `effort` เป็น `low`/`medium` แทน** ประหยัดพอกันและไม่พัง

### Opus 5 ขยายขอบเขตงานเอง
มีแนวโน้มเพิ่มขั้นตอนที่ไม่ได้ขอ · ถ้าเจอ ให้ใส่คำสั่งจำกัดขอบเขตใน prompt แทนการแก้ทีละครั้ง
