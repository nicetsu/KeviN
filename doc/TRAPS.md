## ความปลอดภัย

### `service_role` key ห้ามหลุดไปฝั่งเบราว์เซอร์
กุญแจนี้ข้าม RLS ได้ทั้งหมด ให้อยู่แค่ใน Edge Function เท่านั้น
ฝั่ง Next.js ใช้ `anon key` คู่กับ RLS · ตัวแปรที่ขึ้นต้น `NEXT_PUBLIC_` ทุกตัวไปอยู่ใน bundle ที่ผู้ใช้เปิดดูได้

### API key ของผู้ช่วยห้ามอยู่ฝั่งเบราว์เซอร์
ใครก็เปิดดูโค้ดฝั่งเบราว์เซอร์ได้ แล้วเอาคีย์ไปใช้จนโควตาหมดหรือบิลบาน
**ตัวแปรที่ขึ้นต้น `NEXT_PUBLIC_` ทุกตัวไปอยู่ใน bundle** — ห้ามตั้งชื่อคีย์แบบนั้นเด็ดขาด

> เดิมข้อนี้เขียนว่า "ต้องผ่าน Edge Function เสมอ" · **แก้แล้ว 31 ส.ค.** ตอนเขียนกฎยังไม่มี
> เซิร์ฟเวอร์ Next.js ในระบบ · เจตนาของกฎคือ "key ห้ามอยู่ฝั่งเบราว์เซอร์" ซึ่ง Route Handler
> บน Vercel ก็ตอบได้ และได้ auth จาก `proxy.ts` กับ region `hnd1` มาฟรี
> · Edge Function ยังทำงานเดิมคือรับ pg_cron แล้วยิง push

### เสียงต้องต่อจากเบราว์เซอร์ตรง ห้ามแบกผ่านเซิร์ฟเวอร์เรา
Vercel เป็น serverless ถือ WebSocket ยาว ๆ ไม่ได้ · ทางออกคือ **ephemeral token**
เซิร์ฟเวอร์เอา API key แลก token อายุสั้นแล้วให้เบราว์เซอร์ถือไปต่อเอง
**ล็อก config ไปกับ token ตอนสร้าง** คนที่ขโมย token ไปจึงเปลี่ยน prompt หรือชุด tool ไม่ได้

**แต่ tool ต้องวิ่งกลับมาที่เซิร์ฟเวอร์เราเสมอ** — ตัวกรอง Area อยู่ที่นั่น
ให้เบราว์เซอร์ถาม Supabase ตรง ๆ ง่ายกว่ามาก **แต่คือการข้ามตัวกรอง**

### MCP ให้สิทธิ์รัน SQL ดิบ
Supabase เองแนะนำให้ใช้ MCP กับข้อมูลที่ไม่ใช่ production แต่เคสเรากลับกัน — ข้อมูลนี้คือของจริงและต้องเขียนได้
ทางลดความเสี่ยงที่ต้องทำครบทั้งสี่: `project_ref` + `features=database,docs` · CHECK constraint + RLS · prompt บังคับยืนยันก่อนเขียน · ใช้ `archived_at` แทน `DELETE`

## การแจ้งเตือน

### iOS ต้องติดตั้งลงหน้าจอโฮมก่อนถึงจะรับ push ได้
Safari บน iPhone ไม่ให้เว็บทั่วไปส่ง push — ต้องกดปุ่มแชร์ → "เพิ่มลงหน้าจอโฮม" → เปิดจากไอคอน → แล้วค่อยขอสิทธิ์
**ถ้าไม่ทำหน้าจอสอนขั้นตอนนี้ไว้ จะกลายเป็นบั๊กที่หาสาเหตุไม่เจอในอีกสามเดือน**
ให้แสดงคำแนะนำเฉพาะเมื่อตรวจพบว่าเปิดจาก Safari บน iOS และยังไม่ได้ติดตั้ง — ไม่งั้นรกหน้าจอคนใช้ Android

### VAPID key เปลี่ยนไม่ได้
สร้างคู่กุญแจครั้งเดียวแล้วเก็บให้ดี · ถ้า regenerate ใหม่ subscription เก่าทั้งหมดตายทันที ทุกเครื่องต้องกดอนุญาตใหม่หมด

### push ซ้ำเพราะ cron รอบทับกัน
cron รันทุกนาที ถ้ารอบก่อนยังไม่จบจะยิงซ้ำ
ต้องเขียน `notified_at` **ในคำสั่งเดียวกับที่เลือกแถว** — ใช้ `claim_due_reminders()` ที่มีใน SCHEMA.sql แล้ว
**ห้ามแยกเป็น `SELECT` แล้วค่อย `UPDATE`** ต่อให้อยู่ใน transaction เดียวกัน

### Vercel Cron แพลนฟรีรันได้วันละครั้ง
เตือน "อีก 30 นาทีมี quiz" ไม่ได้ · นี่คือเหตุผลที่เลือก pg_cron ตั้งแต่แรก อย่าเผลอย้ายกลับ

## ความเร็ว

### Vercel ไม่ได้เดา region ให้ — ค่าเริ่มต้นคือเวอร์จิเนีย
ไม่มี `vercel.json` = ฟังก์ชันไปรันที่ `iad1` ไม่ว่าผู้ใช้กับฐานข้อมูลจะอยู่ไหน
เคสเรา ผู้ใช้อยู่ไทย DB อยู่โตเกียว แต่ฟังก์ชันอยู่สหรัฐฯ ทุก query จึงข้ามแปซิฟิกไปกลับ
ดูได้จาก header `X-Vercel-Id` — `sin1::iad1` แปลว่าเข้า edge สิงคโปร์ แต่รันที่เวอร์จิเนีย

**ให้ฟังก์ชันอยู่ region เดียวกับฐานข้อมูล ไม่ใช่ใกล้ผู้ใช้** — หนึ่งหน้ามี query หลายรอบ
แต่ขาเบราว์เซอร์มีรอบเดียว

### `next build` ทับ dev server ที่รันอยู่ แล้วเสิร์ฟของค้างเงียบ ๆ
`next dev` กับ `next build` ใช้โฟลเดอร์ `.next` ร่วมกัน · ถ้ารัน build ตอนที่ dev server ยังรันอยู่
production build จะเขียนทับไฟล์ที่ dev server กำลังเสิร์ฟ แล้ว dev server เสิร์ฟของครึ่ง ๆ กลาง ๆ ต่อไป
**ไม่มี error ไม่มีคำเตือน** — หน้าเว็บขึ้น 200 ปกติ แต่เป็นโค้ดหรือ CSS ของรอบก่อน

เคยทำให้ตามหาบั๊กสีในปฏิทินอยู่นาน ทั้งที่โค้ดถูกมาตั้งแต่แรก
เบาะแสคือ **ข้อความบนจอเป็นของเวอร์ชันกลางทาง** ที่ไม่มีอยู่ในไฟล์แล้ว

**ถ้าจะรัน build ให้ปิด dev server ก่อน** และถ้าเจออาการแปลก ๆ ให้ `rm -rf web/.next` แล้วเปิดใหม่
· ฝั่งเบราว์เซอร์ต้องกด Ctrl+Shift+R ด้วย เพราะ CSS เก่าค้างในแคชได้
· CSS เก่าที่ไม่มี custom property ตัวใหม่จะทำให้ `var(--x)` หาค่าไม่เจอ แล้วสีกลายเป็นใส มองไม่เห็น

### `getUser()` ยิงเน็ตทุกครั้ง
ชื่อฟังก์ชันชวนให้คิดว่าอ่านจาก cookie แต่มันถามเซิร์ฟเวอร์ Supabase จริงทุกครั้ง
ถ้าเรียกทั้งใน proxy และใน action = จ่ายสองรอบต่อการกดหนึ่งครั้ง
ในเว็บนี้ `proxy.ts` ยืนยันให้แล้วทุก request จึงเหลือใช้ `getClaims()` (ตรวจในเครื่อง) ที่ action

## Supabase จากฝั่งเซิร์ฟเวอร์

### `update()` หลายคำสั่งพร้อมกันต้องมี `.select()` ไม่งั้นไม่เขียน
`reorderItems` ยิง `supabase.from('items').update(...)` หลายตัวพร้อมกันผ่าน `Promise.all`
**ไม่มี error ไม่มี rowcount และไม่มีแถวไหนถูกเขียนเลย** ลากแล้วดูเหมือนได้ กด F5 ทีลำดับเด้งกลับหมด
ใส่ `.select('id')` ต่อท้ายแล้วเขียนติดครบทันที

สังเกตว่า `toggleDone`/`archiveItem` ที่ยิงคำสั่งเดียวไม่มี `.select()` เขียนติดปกติ (ตรวจจาก
`updated_at` ในข้อมูลจริงแล้ว) — กลไกที่แท้จริงยังไม่ได้พิสูจน์ รู้แค่ว่าเงื่อนไขนี้ทำให้พัง

**กฎที่ใช้ไปก่อน:** เขียนข้อมูลเมื่อไหร่ให้ `.select()` แล้วเช็กจำนวนแถวที่ได้กลับมาทุกครั้ง
`update` ที่ไม่โดนสักแถวถือว่า "สำเร็จ" ในสายตา PostgREST — ถ้าไม่นับแถวเอง จะไม่มีวันรู้ว่าพัง

## กิจกรรม (events)

### `week_offsets` ไม่ใช่ที่เก็บ "ฉันจะไม่ไป"
`week_offsets` แปลว่า **สัปดาห์นั้นไม่มีคาบ** (มหาลัยหยุด · สัปดาห์สอบ · Commencement Week)
การเอาไปใช้แทนความหมาย "คาบมีอยู่แต่ไม่ไป" ให้ผลบนปฏิทินที่หน้าตาถูกต้องเป๊ะ **แต่ทำลายข้อมูลถาวร**

- ย้อนดูแล้วแยกไม่ออกว่าวันนั้นหยุดจริงหรือโดดเรียน
- วิชาที่มีหลายคาบในสัปดาห์เดียว (บรรยาย + แล็บ) จะหายทั้งหมด ไม่ใช่คาบเดียว
- เลิกทำไม่ได้ เพราะไม่มีอะไรบันทึกว่าเลขสัปดาห์ไหนถูกลบ

ที่เก็บที่ถูกต้องคือ **`time_offsets`** (`skipped = true`) ซึ่งไม่แตะเวลาจริงเลย และคืนค่าได้ด้วยการลบแถว
· `doc/CLAUDE-PROJECT-PROMPT.md` มีกติกาข้อนี้กำกับ Claude ไว้แล้ว

### ตัดเวลาด้วยค่าที่อยู่นอกช่วงของคาบ
`time_offsets.attend_from` / `attend_to` ที่ตกนอกบล็อกจริง (พิมพ์ผิด หรือคาบเปลี่ยนเวลาทีหลัง)
ถ้าเอามาใช้ตรง ๆ จะได้บล็อกยาวศูนย์หรือกลับหัว แล้ว**คาบหายจากปฏิทินเงียบ ๆ**
`calendar_entries()` จึงใช้ค่านั้นก็ต่อเมื่ออยู่ในช่วงจริงเท่านั้น ไม่งั้นเมินแล้วใช้เวลาเดิม
— การตัดที่ไม่มีผล ดีกว่าคาบที่หายไปโดยไม่รู้ตัว

### `on delete set null` บน FK สองคอลัมน์ ต้องระบุคอลัมน์
`items.event_id` อ้าง `events(id, project_id)` เพื่อให้ Postgres บังคับเองว่างานกับ event อยู่ project เดียวกัน
ถ้าเขียน `on delete set null` เปล่า ๆ **Postgres จะพยายามเซ็ต `project_id` เป็น null ด้วย** ซึ่งชน NOT NULL แล้วการลบ event จะล้มทั้งคำสั่ง
ต้องเขียน `on delete set null (event_id)` ระบุคอลัมน์ไว้ (ต้องการ Postgres 15 ขึ้นไป · ของจริงรัน 17.6)

### CHECK ใส่ `at time zone` ไม่ได้
Postgres รับเฉพาะฟังก์ชัน IMMUTABLE ใน CHECK แต่ `timestamptz at time zone 'Asia/Bangkok'` เป็น **STABLE**
กฎแบบ "ห้าม event ข้ามเที่ยงคืน" หรือ "กำหนดการต้องอยู่ในช่วงของงาน" จึงบังคับที่ DB ไม่ได้ตรง ๆ
ที่ทำได้คือเงื่อนไขที่เป็นเลขคณิตล้วน เช่น `ends_at <= starts_at + interval '30 days'`

### `"24:00:00"` ประกอบเป็น `Date` ไม่ได้
`calendar_entries()` ให้บล็อกที่วิ่งชนเที่ยงคืนมาเป็น `end_time = '24:00:00'`
`new Date('2026-09-05T24:00:00+07:00')` คืน **Invalid Date** เงียบ ๆ ไม่ throw
ต้องแปลงเป็นเที่ยงคืนของวันถัดไปเอง — ทำไว้แล้วใน `entryEndMs()` ที่ `web/lib/calendar.ts` **ห้ามคำนวณเองที่อื่น**

### คีย์ของบล็อกปฏิทินต้องมีวันที่ด้วย
`source_id` อย่างเดียวไม่พอสองชั้น — คาบเรียนใบเดียวโผล่ทุกสัปดาห์ และ event ข้ามคืนใบเดียวถูกหั่นเป็นหลายบล็อกที่ใช้ id เดียวกัน
ใช้ `entryKey()` ที่รวม `kind` + `source_id` + `occurs_on`

### `shape()` ที่ใส่ `event_id: null` ทุกครั้ง = ปลดการผูกเงียบ ๆ
แผงแก้ไข (S7) สร้าง `ItemDraft` โดยไม่รู้จัก event เลย
ถ้า `shape()` ใส่ `event_id: null` ลงไปเสมอ การกดแก้ชื่องานเฉย ๆ จะปลดงานออกจากกิจกรรมโดยไม่มีอะไรเตือน
กฎคือ **ละคีย์ไว้ = ไม่แตะ · ใส่ `null` = ปลด** (ดู `web/app/actions/items.ts`)

### เปิดหน้าแก้แล้วกดบันทึก เวลาที่อนุมานจะกลายเป็นเวลาที่กรอกเอง
`event_agenda.end_time` ที่เป็น null ถูกเติมค่าตอน**แสดงผล** ไม่ใช่ตอนเก็บ
หน้าแก้ต้องคืนช่องเวลาจบให้เป็นช่องว่างเมื่อ DB เก็บ null ไว้ ไม่ใช่เอาค่าที่เติมแล้วมาใส่
ไม่งั้นแค่เปิดหน้าแก้แล้วกดบันทึก ข้อมูลที่เคยยืดหยุ่นจะถูกตรึงถาวร

## ประตูที่สาม (แชตและเสียง)

ทุกข้อในหัวข้อนี้**เจอจากการรันจริง ไม่ใช่จากการอ่านโค้ด** — และสองข้อแรกเป็นชนิดที่
รอบแรกดูเหมือนทำงานปกติทุกอย่าง

### Gemini 3 บังคับให้ส่ง `thoughtSignature` กลับไปด้วย
โมเดลแนบ `thoughtSignature` มากับ part ที่เป็น `functionCall`
ถ้าประกอบ turn ของโมเดลขึ้นใหม่เองแล้วใส่แค่ `functionCall` จะได้
**400 Function call is missing a thought_signature** ในรอบถัดไป

**รอบแรกทำงานปกติทุกอย่าง** — โมเดลเรียก tool ได้ tool ทำงานได้ พังตอนส่งผลกลับเข้าไป
กฎคือ **push `parts` ชุดเดิมกลับไปทั้งก้อน ห้ามแกะประกอบใหม่**

### เอกสารหน้าแนะนำของ Live API บอกชื่อฟิลด์ผิด
หน้าแนะนำใช้คำว่า `liveConnectConstraints` ซึ่ง v1beta ตอบ **400 Unknown name**
ชื่อที่ถูกอยู่ในหน้า API reference คือ **`bidiGenerateContentSetup`**
และรูปข้างในเป็นแบบเดียวกับ setup message ของ WebSocket **ไม่ได้ห่อด้วย `config` อีกชั้น**

บทเรียนกว้างกว่านั้น: **หน้าแนะนำกับหน้า reference ของ Google ไม่ตรงกัน** ให้เชื่อ reference

### Live API ไม่รับ language code เลย
เอกสารระบุว่าโมเดล native audio "เลือกภาษาเองและไม่รองรับการตั้ง language code"
**ทางเดียวที่จำกัดภาษาได้คือสั่งใน system instruction** ซึ่งเป็นแรงกด ไม่ใช่การล็อก

ของจริงที่เจอ: พูดไทยแล้วถอดเสียงเป็นจีน ฮินดี เกาหลี สลับกันในสายเดียว
จุดที่พังคือ**ตอนฟังไม่ชัด** — มันไปเดาเป็นภาษาอื่นแทนที่จะถามซ้ำ
กฎใน `lib/ai/lang.ts` จึงต้องสั่งเรื่องนี้ตรง ๆ ไม่ใช่แค่บอกว่าให้ใช้ภาษาอะไร

### ตัวกรอง Area ผูกกับ **ชื่อ** ไม่ใช่ id — เปลี่ยนชื่อแล้วพังเงียบ
`VISIBLE_AREAS` ใน `lib/ai/visibility.ts` เทียบด้วยชื่อ Area ตรง ๆ
ถ้าเปลี่ยนชื่อ Area ใน DB แล้วลืมแก้ที่นี่ **ผู้ช่วยจะมองไม่เห็น Area นั้นทันที
โดยไม่มี error** — มันแค่ตอบว่าไม่มีข้อมูล ซึ่งดูเหมือนคำตอบปกติทุกอย่าง

ที่ยังผูกกับชื่อแทน id เพราะ id เป็น uuid ที่อ่านไม่รู้เรื่อง และไฟล์นั้นต้องอ่านออก
ทันทีว่าอะไรออกจากเครื่องได้บ้าง — แลกด้วยการต้องจำว่าเปลี่ยนชื่อแล้วต้องมาแก้

**เปลี่ยนชื่อ Area ต้องเรียงลำดับด้วย** `areas` มี `unique(user_id, name)`
ถ้าชื่อใหม่ไปชนชื่อที่ยังมีอยู่ (เช่น `Financial`→`Personal` ตอนที่ยังมี `Personal`)
ต้องปล่อยชื่อนั้นให้ว่างก่อน

### `voiceName` มีผลไม่เท่ากันในแต่ละภาษา
ตั้ง `speechConfig.voiceConfig.prebuiltVoiceConfig.voiceName` เป็น `Fenrir` แล้ว
**เสียงตอนพูดไทยเปลี่ยนตาม แต่ตอนพูดอังกฤษไม่เปลี่ยน**

แปลว่า `speechConfig` ถูกใช้จริง (ไม่ได้ถูกเมิน) แต่โมเดล native audio
**มีเสียงของตัวเองสำหรับบางภาษาที่ไปทับค่าที่เราตั้ง**
จึงต้องเลือกเสียงแยกตามภาษาที่ตอบ ไม่ใช่ตั้งค่าเดียวแล้วคาดว่าจะเหมือนกันทุกภาษา

⚠️ **"ไม่ส่ง `speechConfig` เลย" ไม่เท่ากับ "ส่งชื่อเสียงที่เป็นค่าเริ่มต้น"**
ถ้าอยากได้เสียงเริ่มต้นของโมเดล ต้องไม่ส่งฟิลด์นั้นไปเลย

### โมเดลแต่งลิงก์ขึ้นมาเองเวลาต้องปฏิเสธ
ตอบว่าไปแก้ได้ที่ `https://tasks.google.com/` ซึ่งไม่ใช่ของระบบนี้เลย
พอสั่งใน prompt ว่าห้ามลิงก์นอกระบบ **มันเปลี่ยนไปแต่ง path ภายในปลอมแทน** (`/items/overdue`)

รากของปัญหาคือ **tool ไม่ได้คืนลิงก์มาให้** มันเลยไม่มีอะไรจะยื่น
แก้สองทาง: ให้ทุก tool คืนคีย์ `ลิงก์` เสมอ **และ** ตรวจตอนส่งออกด้วย `lib/chat/links.ts`
— prompt ห้ามได้แค่สิ่งที่โมเดลตั้งใจ ด่านตอนส่งออกกันได้ทุกกรณี

**แต่ห้ามอย่างเดียวไม่พอ** (เจอต่อ 31 ส.ค.) — พอผู้ใช้ถามลอย ๆ ว่า "แก้ข้อมูลได้ไหม"
โดยไม่เจาะจงรายการไหน โมเดลไม่มีลิงก์จาก tool ให้ใช้ มันเลยแต่งอีกจนได้
ตัวกรองตัดทิ้งถูกต้อง แต่ผู้ใช้เห็นประโยคทางตันว่า "แก้ได้ที่นี่ครับ: (ลิงก์ไม่ถูกต้อง)"
**prompt ต้องบอกด้วยว่าใช้อะไรได้** ไม่ใช่บอกแค่ว่าห้ามอะไร — ตอนนี้ระบุหน้าประจำสี่หน้าไว้

### ผู้ช่วยครอบลิงก์ด้วย backtick แล้วมันกลายเป็นของกดไม่ได้
เขียน `` `/library` `` มาแทนที่จะเขียน `/library` เฉย ๆ ตัวเรนเดอร์เห็นเป็นโค้ด
ผลคือได้ลิงก์ที่ถูกต้องแต่**กดไม่ได้** ซึ่งคือปัญหาเดิมในรูปแบบใหม่

สาเหตุคือ prompt เองเขียนตัวอย่างเส้นทางไว้ใน backtick โมเดลเลยลอกสไตล์นั้นมา
แก้ทั้งสองข้าง: prompt เขียนเส้นทางเปล่า ๆ **และ** `MessageText.tsx` แปลงโค้ดที่เป็น
เส้นทางจริงให้เป็นลิงก์อยู่ดี — **สิ่งที่ prompt สั่ง กับสิ่งที่โมเดลทำ ไม่เคยตรงกัน 100%**

### รูปที่ค้างอยู่ในประวัติ = ส่งไป Google ซ้ำทุกครั้งที่พิมพ์ต่อ

มติคือ **"ไม่เก็บรูป · รูปมีชีวิตแค่คำขอเดียว"** ซึ่งฟังดูเหมือนแค่ไม่ต้องมี bucket
**แต่ที่ทำให้มันเป็นจริงได้จริงคือการที่ `contents` ถูกประกอบใหม่จากข้อความล้วน
ทุกคำขอ** ไม่ใช่การสะสมไว้ในตัวแปรเดียวข้ามเทิร์น

ถ้าเก็บ `contents` ไว้แล้วต่อท้ายไปเรื่อย ๆ (ซึ่งเป็นวิธีที่เขียนง่ายที่สุด)
รูปใบเดิมจะถูกอัปโหลดใหม่ทุกครั้งที่ผู้ใช้พิมพ์ต่อ · **ไม่มีอะไรผิดบนจอเลย**
คำตอบยังถูก การ์ดยังขึ้น แค่ค่าใช้จ่ายด้านความเป็นส่วนตัวถูกจ่ายซ้ำ ๆ เงียบ ๆ

⚠️ **ชุดวัดต้องเลียนแบบข้อนี้ด้วย** — `askChat()` ใน `test/accuracy/chat.ts`
แทน part ของรูปด้วย `[รูป] …` ก่อนเข้าเทิร์นที่สอง · ถ้าไม่ทำ เคส "รูปเก่ามองไม่เห็นแล้ว"
จะผ่านตลอดเพราะโมเดล**ยังเห็นรูปอยู่จริง ๆ** ในชุดวัด ทั้งที่ของจริงมันไม่เห็น

### รูปจากกล้องเป็นแนวนอนเสมอ ธงหมุนอยู่ใน EXIF

รูปแนวตั้งที่ถ่ายจากมือถือเก็บพิกเซลเป็นแนวนอนพร้อมธง `orientation`
`<img>` กับ `createImageBitmap()` **ค่าเริ่มต้นไม่เท่ากัน** — ถ้าวาดลง canvas
โดยไม่สั่ง `imageOrientation: 'from-image'` จะได้รูปตะแคง **โดยไม่มี error**
แล้วโมเดลอ่านตัวหนังสือไม่ออกทั้งใบ ซึ่งดูเหมือน "โมเดลอ่านรูปไม่เก่ง"

ผลพลอยได้ของการวาดใหม่คือ **EXIF หายทั้งก้อน รวมพิกัด GPS** ซึ่งเป็นสิ่งที่
ต้องการอยู่แล้ว — แต่ต้องรู้ว่ามันเป็นผลพลอยได้ ไม่ใช่สิ่งที่โค้ดบรรทัดไหนสั่ง
· วันไหนเปลี่ยนไปส่งไฟล์เดิมตรง ๆ เพราะเห็นว่า "เร็วกว่า" พิกัดจะกลับมาทันที

### body ของ error ฝั่ง Google ห้ามขึ้นจอ — และ 5xx ไม่ใช่โควตาหมด

`rateLimitOr()` เคยต่อ `body.slice(0, 200)` เข้าไปในข้อความที่ผู้ใช้เห็น ทำให้
เจอ 503 ทีไรได้ **JSON ก้อนหนึ่งกลางห้องแชต** (เจ้าของเจอบนเครื่องจริง 9 ก.ย. 2026
ตอนแนบรูปโปสเตอร์) · มันอ่านเหมือนแอปพัง ไม่ได้บอกว่าต้องทำอะไรต่อ
ทั้งที่ความจริงคือฝั่ง Google แน่นชั่วคราวแล้วหายเอง

**5xx กับ 429 ต้องแยกกันให้ขาด** — 429 รายวันลองใหม่ไม่ช่วย ส่วน 5xx ลองใหม่
มีโอกาสผ่านสูงมาก · การเหมารวมทำให้ผู้ใช้เลิกลองทั้งที่กดอีกทีก็ได้แล้ว

⚠️ **ชุดวัดยิงซ้ำเมื่อ 5xx มาตั้งแต่ต้น แต่แอปจริงไม่เคยยิงซ้ำ** —
`test/accuracy/chat.ts` มี `generateOrRetry` ที่ถอย 2 วินาทีแล้วลองใหม่ถึงสามครั้ง
· แปลว่า **ชุดวัดทนกว่าของจริง** และมันจะรายงานว่า "ผ่าน" ในสถานการณ์ที่ผู้ใช้จริง
เห็น error · เป็นความต่างที่ซ่อนปัญหาทั้งชนิดไว้ไม่ให้ถูกวัดเจอ

ตอนนี้ `fetchOrRetry` ใน `lib/chat/gemini.ts` ยิงซ้ำ 5xx สองครั้ง (600ms · 2s)
**ก่อนเริ่มอ่านสายเท่านั้น** — ยิงซ้ำหลังข้อความเริ่มไหลจะได้คำตอบซ้อนกันสองชุด
· **ไม่ยิงซ้ำเมื่อ 429** เพราะมีคนถือมือถือรออยู่ และข้อความบอกอยู่แล้วว่าให้รอเท่าไร

### คำขอที่ล้ม ต้องไม่กินสิ่งที่ผู้ใช้พิมพ์และรูปที่แนบไปด้วย

`ARCHITECTURE.md` §9 เขียนกฎไว้ตั้งแต่ต้นว่า *"บันทึกไม่สำเร็จ → ไม่ทิ้งสิ่งที่พิมพ์
เก็บไว้ในช่องเดิม + ปุ่มลองใหม่"* · **แต่เส้นทางส่งแชตไม่เคยทำตาม** — มันลบฟอง
ที่กำลังไหลทิ้งแล้วจบ ส่วนข้อความกับรูปหายไปกับมัน

ราคาสูงเป็นพิเศษหลังมีการแนบรูป: ผู้ใช้เพิ่งเล็งถ่ายโปสเตอร์ แล้วต้องเลือกรูปใหม่
ทั้งที่ความผิดอยู่ฝั่งเซิร์ฟเวอร์และ **หายเองได้ถ้ากดส่งอีกที**

⚠️ ตอนถอนคืนต้องถอน **ทั้งฟองของผู้ใช้** ไม่ใช่แค่ฟองที่กำลังไหล — ไม่งั้น
object URL เดียวกันจะอยู่สองที่ (ฟองเก่า + ช่องพิมพ์) แล้วการคืน URL ครั้งเดียว
ทำให้รูปในฟองกลายเป็นกรอบว่าง · และธงที่ใช้ถอนต้อง**แยกจาก `pending`**
เพราะ `pending` คือฟองของผู้ช่วยที่ตัวอัปเดต delta ตามหาอยู่

### `tool ล่ม` ห้ามกลายเป็นรายการว่าง
ถ้าคืน `rows: []` แทน error โมเดลจะพูดอย่างมั่นใจว่า "พรุ่งนี้ไม่ติดอะไรเลย"
ทั้งที่แค่ query ไม่ผ่าน — **คำโกหกที่แพงที่สุดที่แอปนี้พูดได้** และผิดหลัก UX ข้อ 5 ตรง ๆ
เรื่องเดียวกันกับ `hidden`: กรองออกไปกี่แถวต้องบอก ไม่ใช่เงียบ

`100vh` วัดจากความสูงของ viewport ตอนแถบเบราว์เซอร์ยังอยู่ครบ · พอคีย์บอร์ดเด้งขึ้นมา

ใช้ `dvh` แทน แล้วคง `vh` ไว้บรรทัดก่อนหน้าเป็นค่าสำรองให้เบราว์เซอร์ที่ยังไม่รู้จัก

### flex item ที่ต้อง scroll ต้องมี `min-height: 0`
ค่าเริ่มต้นของ flex item คือ `min-height: auto` ซึ่งแปลว่า **ห้ามหดเล็กกว่าเนื้อหา**

ต้องใส่ `min-height: 0` ให้มันหดได้ก่อน `overflow` ถึงจะมีความหมาย

ซึ่ง **เก็บ ACL เดิมไว้ทั้งหมด** · แก้ฟังก์ชันกี่รอบก็ไม่มีอะไรเตือน และ diff

⚠️ **ก่อน revoke ต้องรู้ก่อนว่า trigger ยังยิงได้ไหม** — ถ้าเดาผิดคือ**สมัครไม่ได้

### ลบ `project` แล้ว `items` หายตามทั้งกอง

### `Group` ที่ตัด children ทิ้งตอนว่าง ฆ่าแถบเลิกทำ

### `deviceId` ของไมค์ต้องใช้ `ideal` ไม่ใช่ `exact`
`exact` ทำให้ `getUserMedia` ทั้งคำสั่งล้มด้วย `OverconstrainedError` เมื่ออุปกรณ์นั้น

และค่าที่จำไว้ต้อง**ปัดกลับเป็นอัตโนมัติเองเมื่ออุปกรณ์หายไป** ไม่งั้นหน้าจอจะโชว์ชื่อ
อุปกรณ์ที่ไม่มีอยู่แล้วค้างไว้

### ชื่อไมค์ถูกปิดไว้จนกว่าจะได้สิทธิ์
`enumerateDevices()` คืน `label` ว่างถ้ายังไม่เคยอนุญาตไมค์ — ก่อนโทรครั้งแรก

### รายการอุปกรณ์เป็น external store ไม่ใช่ค่าที่อ่านครั้งเดียว

รันตรวจงานระหว่างพัฒนาแล้วทุกหน้าเรนเดอร์**ว่างเปล่าโดยไม่มี error สักบรรทัด**

ข้อนี้อยู่ในไฟล์นี้อยู่แล้วแต่ยังพลาดซ้ำ — **ห้ามรัน `next build` ตอน dev server ยังทำงาน**
ถ้าต้องตรวจ ให้หยุด dev server ก่อน แล้วล้าง `.next` หลังเสร็จเสมอ

### **morph ข้ามหน้าไม่ทำงานเมื่อมี `loading.tsx` คั่น**
พยายามให้ชื่อวิชาในคลัง *เดินทาง* ไปเป็นหัวของหน้าวิชา — ครอบ `<ViewTransition name>`
ทั้งสองฝั่งตาม pattern ที่เอกสาร Next แนะนำเป๊ะ **แต่ไม่ติด**

สาเหตุที่หาเจอตอนหน่วง transition เป็น 6 วินาทีแล้วดูภาพทีละเฟรม — console บอกว่า
`TimeoutError: Transition was aborted because of timeout in DOM update`

ลำดับจริงคือ **คลัง → โครงร่าง → หน้าวิชา** · ตอนโครงร่างขึ้น ฝั่งเก่าหายไปแล้ว
และโครงร่างไม่มี element ชื่อเดียวกัน จึง**ไม่มีคู่ให้ morph** · ต่อให้ปิด `loading.tsx`
ก็ยังชนเพดานเวลาของเบราว์เซอร์ เพราะทุกหน้าเป็น `force-dynamic` ต้องรอเซิร์ฟเวอร์เสมอ

**สรุปสุดท้าย (1 ก.ย. 2026 · หลังทดสอบบน production build 6 รอบ): ทำไม่ได้ในสถาปัตยกรรมนี้**

Next.js ทำ view transition **สองรอบต่อการเปลี่ยนหน้าหนึ่งครั้ง** บน route ที่เป็น
`force-dynamic` — รอบแรกตอนเริ่มโหลด รอบสองตอนเนื้อมาถึง เห็นจากการดัก
`document.getAnimations()` ทุกครั้งที่ทดสอบ:

```
รอบ 1: old(root) · old(area-A) · old(area-B) …        ← ของเก่าหายไป
รอบ 2: old(_t_1_) · new(area-A)                        ← ของใหม่มา แต่คู่ไม่อยู่แล้ว
```

**ไม่มี `::view-transition-group(area-*)` สักครั้ง** ซึ่งเป็น pseudo-element ที่ทำ morph จริง
มีแต่ `group(root)` · `_t_1_` คือโครงร่างจาก `loading.tsx` (ยืนยันได้เพราะมันเล่น `reveal-fade`)

ลองแล้วไม่ช่วย: ลบ `loading.tsx` ของทุก segment ในเส้นทาง · ลบ `<Content>` wrapper ·
ใช้ `<ViewTransition name>` ของ React · ใช้ `view-transition-name` ของ CSS ตรง ๆ

⚠️ **React ไม่ยอมใส่ `viewTransitionName` ผ่าน style object** (`getComputedStyle` คืน `none`)
ต้องส่งผ่าน custom property แล้วให้ CSS ตั้งชื่อ — แต่ถึงตั้งได้ก็ยังไม่จับคู่อยู่ดี

⚠️ **`loading.tsx` ใน segment ครอบ route ลูกทุกตัวที่ไม่มีของตัวเอง**
`app/library/loading.tsx` จึงเป็นโครงร่างของ `/library/[areaId]` ด้วย

**ทางที่ใช้ได้จริง — ประกอบจากสองรอบ (ยืนยันแล้วบน production build)**

⚠️ **ไม่มี `::view-transition-new(root)` เลย** ทั้งสองรอบ (ดักทุก 30/60/120/260/400 ms
ไม่เจอสักครั้ง) — เบราว์เซอร์ไม่ทำ snapshot ฝั่งใหม่ของ root เพราะ DOM ยังไม่พร้อม
**ขาออกกับขาเข้าจึงต้องมาจากคนละรอบ:**

| รอบ | pseudo-element | animation | เห็นเป็น |
|---|---|---|---|
| 1 | `old(root)` | `nav-out-left` / `nav-out-right` | หน้าเก่าเลื่อนออกตามทิศทาง |
| 2 | `new(_t_N_)` | `reveal-fade` + `reveal-rise` | เนื้อใหม่เลื่อนเข้าจากขวา |

`reveal-rise` จึงเปลี่ยนจากเลื่อน**ขึ้น** เป็นเลื่อนเข้าจาก**ขวา** — มันคือขาเข้าตัวจริง
ตัวเดียวที่มี · ระยะสั้น 18px เพราะเล่นทุกการเปลี่ยนหน้ารวมสลับแท็บล่างที่ควรนิ่ง

**การ์ดที่ขยายเป็นหัวของหน้าถัดไป ทำได้ — แต่ต้องทำเอง ไม่ใช่ View Transition**
`lib/cardFlight.ts` จดตำแหน่งการ์ดตอนกดลง `sessionStorage` แล้วหน้าถัดไปอ่านไปตั้ง
ท่าเริ่มต้นของหัวด้วย `element.animate()` — **เราบอกเองว่าของมาจากไหน**
จึงไม่ต้องรอให้เบราว์เซอร์จับคู่ และไม่ติดข้อจำกัดสองรอบข้างบนเลย

สามอย่างที่ต้องมี ไม่งั้นพังเงียบ:
- **หมดอายุ** (400ms) — การเคลื่อนไหวที่มาช้ากว่าการกระทำอ่านไม่ออกว่าเกี่ยวกัน
- **ลบค่าทันทีที่อ่าน** ไม่ว่าจะใช้ได้หรือไม่ — ไม่งั้นค้างข้ามการนำทางครั้งถัดไป
  แล้วหัวของหน้าอื่นบินมาจากตำแหน่งที่ไม่เกี่ยวอะไรเลย (กดแล้วกดย้อนกลับเร็ว ๆ)
- **ตั้ง `transform-origin` ก่อน `animate()`** — Web Animations API อ่านค่านี้จาก
  element ไม่ใช่จาก keyframes ตั้งทีหลังจะย่อจากกึ่งกลางแล้วตำแหน่งเพี้ยนไปครึ่งหนึ่ง

⚠️ **ต้องมี `<Content>` ครอบหน้าปลายทาง** ไม่งั้นไม่มี `new(_t_N_)` ให้เล่นเลย —
ถอด wrapper ออกตอนไล่หา morph แล้วลืมใส่กลับ ผลคือหน้าเก่าเลื่อนออกแล้วจอว่าง
ก่อนหน้าใหม่โผล่มาเฉย ๆ ซึ่ง**ดูเหมือนไม่มี animation เลย**

### **`animation-timeline: view()` ใช้กับ pseudo-element ไม่ได้**
ใส่บน `.acard::before` ตรง ๆ แล้ว `currentTime` **ค้างที่ 50% ตลอด** ไม่ว่าจะเลื่อนยังไง
โดยไม่มี error อะไรเลย — CSS ถูกต้อง `@supports` ผ่าน animation มีอยู่จริงใน `getAnimations()`
แต่ไทม์ไลน์ไม่เดิน

พิสูจน์โดยใส่ animation ตัวเดียวกันบน `.acard` (element จริง) แล้ว `currentTime`
เดินจาก 28% เป็น 100% ตามการเลื่อนทันที — **ต่างกันแค่ pseudo กับ element จริง**

แก้ด้วยการให้ **element จริงเป็นตัวเดินไทม์ไลน์** แล้วส่งค่าให้ pseudo ผ่าน custom property
ที่ register ด้วย `@property` · ⚠️ **ต้อง register** ไม่งั้นเบราว์เซอร์มองว่าเป็นสตริง
แล้ว interpolate ไม่ได้ ค่าจะกระโดดจากต้นไปปลายทันทีแทนที่จะไล่

### `Date.now()` ใน Server Component โดน lint
กฎ `react-hooks` จับว่าเป็น impure function ใน render · `new Date().getTime()` ผ่าน
ทั้งที่ให้ผลเหมือนกัน — เขียนให้ผ่านกฎดีกว่าปิดกฎ เพราะกฎถูกในหลักการ
(Server Component รันครั้งเดียวต่อ request จึงไม่มีปัญหาจริง แต่ Client Component มี)

### FLIP ต้องใช้ `useLayoutEffect` ไม่ใช่ `useEffect`
ถ้าใช้ `useEffect` ผู้ใช้จะเห็นแถว**กระโดดไปที่ใหม่ก่อน** แล้ว animation
ค่อยเริ่มจากตรงนั้น ซึ่งแย่กว่าไม่มี animation เลย

และต้องให้ตัวตนกับ**ทุกแถว** รวมแถวที่ไม่ใช่ item (คาบเรียนไม่มี `id`)
ไม่งั้นครึ่งรายการเดินทางอีกครึ่งกระโดด ซึ่งดูแย่กว่ากระโดดทั้งหมด

### `useSyncExternalStore` กับรายการอุปกรณ์
เขียนเป็น `useEffect` + `setState` แล้ว lint จับ (`set-state-in-effect`)
เพราะ `enumerateDevices()` เป็น async · รูป external store ตรงกับธรรมชาติของมันกว่า
และได้ `devicechange` มาฟรี — **ของที่เปลี่ยนเองได้จากนอก React ควรเป็น store ไม่ใช่ effect**

### เปลี่ยนคีย์ที่เป็นทั้งชื่อเก่าและชื่อใหม่
ตอนเปลี่ยน `areas.color` เป็น `comp`/`pers`/`gen` — `pers` เป็นทั้งชื่อเก่า (General เดิม)

ชั่วคราวแล้วโดน `update` รอบถัดไปเปลี่ยนพร้อมกันทั้งคู่

## หน้าจอและ CSS ที่พังเงียบ ๆ

ทุกข้อในหัวข้อนี้**ไม่มี error สักบรรทัด** มีแต่หน้าจอที่ดูผิด — และเกือบทุกข้อ
ตรวจได้ด้วยการ**วัดค่าจริงในเบราว์เซอร์** ไม่ใช่การอ่านซอร์ส

### SVG ที่ไม่มี `width`/`height` จะกางเต็มที่โดยไม่มี error

ไอคอนในแถบล่าง (`components/Nav.tsx`) เขียนด้วย `viewBox` อย่างเดียว ไม่ใส่ขนาดในแท็ก
ขนาดจริงมาจาก `.nav__item svg { width: 1.3rem; height: 1.3rem }` ใน `app/globals.css`

**ถ้ากฎ CSS นั้นหายไป** เบราว์เซอร์จะไม่แจ้งอะไรเลย แต่จะกาง SVG เป็นขนาดเริ่มต้นของมัน
— วัดจริงได้ **74px ต่อไอคอน** แถบล่างเลยสูง **129px** แทนที่จะเป็น 71px
และปุ่มเพิ่มเร็วก็ไปนั่งทับแถบพอดี ไม่มี error ไม่มี warning มีแต่หน้าจอที่ดูผิด

**ตรวจยังไง** วัดจริงในเบราว์เซอร์ ไม่ใช่ดูโค้ด — `document.querySelector('.nav').getBoundingClientRect().height`
ควรได้ราว 71 บนมือถือ

*เจอ 1 ก.ย. 2026 ตอนใส่ไอคอนลงแถบล่างครั้งแรก*

### เวิร์ดมาร์ก KEVIN เป็นเส้น ไม่ใช่ข้อความ

`components/Nav.tsx` มีคอมโพเนนต์ `Wordmark` ที่เป็น `<path>` เส้นเดียว — คือคำว่า `KEVIN`
ในฟอนต์ Unbounded Medium ที่**แกะเป็นเส้นแล้ว** ไม่ใช่ตัวหนังสือ

**ห้ามเปลี่ยนกลับเป็น `<span>KEVIN</span>` แล้วสั่ง `font-family: Unbounded`** — แอปไม่มีฟอนต์นั้น
ผลคือมันจะ fallback ไป Inter เงียบ ๆ แล้วหน้าตาเปลี่ยนไปโดยไม่มีอะไรฟ้อง

**แก้คำหรือน้ำหนักฟอนต์ต้องแกะเส้นใหม่** ด้วย `fontTools` จากไฟล์ woff2 ของ Google Fonts
(`SVGPathPen` + `TransformPen` กลับแกน y และหารด้วย cap height 750) — **ห้ามแก้ค่าใน `d` ด้วยมือ**

**และ `.nav__item .nav__wordmark` ต้องมีสองชั้น** เพราะ `.nav__item svg` (0,1,1) ชนะ
`.nav__wordmark` (0,1,0) — เขียนชั้นเดียวแล้วคำจะถูกบีบเป็นสี่เหลี่ยม 21×21 เงียบ ๆ

*เจอ 1 ก.ย. 2026 ตอนใส่เวิร์ดมาร์กครั้งแรก*

### `max-width` ที่มี `%` อยู่ด้วย ไม่ได้ลด `max-content` ของรูป

ปุ่มรูปตัวอย่างในฟองข้อความตั้ง `width: fit-content` ไว้แล้ว **แต่วัดจริงได้ 269px
ทั้งที่รูปข้างในกว้าง 208px** — เหลือพื้นที่กดได้ที่**มองไม่เห็น** ข้างรูป 61px
แตะตรงนั้นแล้วรูปเด้งเต็มจอทั้งที่ไม่ได้ตั้งใจกด

สาเหตุคือเพดานอยู่ผิดชั้น: `.msg__thumb img { max-width: min(13rem, 100%) }`
ตอนเบราว์เซอร์คำนวณ `fit-content` ของ**ปุ่ม** มันต้องรู้ `max-content` ของลูกก่อน
· `max-width` ที่มี `100%` ปนอยู่แก้ตอนนั้นไม่ได้ (เพราะ % อ้างอิงของที่ยังไม่รู้ค่า)
มันจึงใช้ความกว้างจริงของไฟล์ (600px) ไปคิด แล้วตกมาเท่ากับที่ว่างในฟองพอดี

**ดูเหมือนกฎไม่ทำงาน ทั้งที่มันทำงานอยู่ แค่คนละชั้นกับที่ตั้งใจ** — `getComputedStyle`
ของรูปคืน `min(208px, 100%)` ถูกต้องทุกอย่าง ตัวที่ผิดคือกล่องรอบนอก

**กฎ: เพดานความกว้างต้องอยู่ที่ตัวที่กำหนดขนาดกล่อง ไม่ใช่ที่รูปข้างใน**
ให้ปุ่มถือ `max-width` แล้วรูปเป็น `width: 100%`

**ตรวจยังไง** วัดทั้งคู่แล้วลบกัน — `btn.getBoundingClientRect().width -
img.getBoundingClientRect().width` ต้องเป็น 0 · ดูจากตาไม่มีทางเห็น
เพราะส่วนเกินเป็นพื้นที่ใส

> ⚠️ ระหว่างไล่ข้อนี้ยังเจอซ้ำอีกว่า **แท็บถือ CSS ฉบับที่แคชไว้** แม้กด reload แล้ว
> — `fetch(href, {cache:'reload'})` เห็นฉบับใหม่ แต่หน้ายังใช้ฉบับเก่า
> ตอนวัดค่าจริงต้องยัด `<link>` ที่ต่อ query กันแคชเข้าไปก่อน ไม่งั้นจะวัดของเก่า
> แล้วสรุปว่า "แก้แล้วไม่มีผล" (ญาติกับข้อ `next build` ทับ dev server)

### CSS ที่ specificity เท่ากัน — ตัวที่มาทีหลังชนะ

เจอสองครั้งในวันเดียว (1 ก.ย. 2026) และทั้งสองครั้ง**ไม่มี error อะไรเลย** มีแต่ของที่หน้าตาไม่เปลี่ยน

- `.nav__wordmark` (0,1,0) แพ้ `.nav__item svg` (0,1,1) → คำถูกบีบเป็น 21×21
- `.page-head--today h1` เขียนไว้**ก่อน** `.page-head h1` ทั้งที่ specificity เท่ากัน (0,1,1) → ขนาดไม่เปลี่ยน

**วิธีตรวจ** อย่าดูจากซอร์ส ให้วัดค่าจริง — `getComputedStyle(el).fontSize` แล้วเทียบกับที่ตั้งใจ
ถ้าตรงกับค่า*เดิม*เป๊ะ ๆ แปลว่ากฎใหม่ไม่ได้ถูกใช้ ไม่ใช่ว่าคำนวณผิด

### ฟองข้อความฝั่งเรากลับด้านสีจากทั้งแอป

ตั้งแต่ 1 ก.ย. 2026 `.msg--me` เป็น**พื้นไล่เฉดม่วงสว่าง ตัวอักษรเข้ม** ซึ่งกลับด้านจากทุกที่ในแอป

**ผลคือสีจางชุดเดิมใช้ในนั้นไม่ได้เลย** — `--faint` บนพื้นนั้นได้คอนทราสต์ **1.06** ที่ปลายเข้ม

**กฎ**: ของใหม่ที่วางบนฟองฝั่งเรา (ลิงก์ · ป้าย · โค้ด · markdown) ต้องคำนวณคอนทราสต์
กับ **`#8878F0` ซึ่งเป็นปลายเข้มสุด** ไม่ใช่กับ `#C3B6FF` ที่สว่างกว่า

### state ใน VoiceCall ไม่ถูกล้างตอนวางสาย

`VoiceCall` **ไม่ได้ remount ตอนสายจบ** — มันแค่ `return` JSX คนละก้อนตาม `call.state`
คอมโพเนนต์ตัวเดิมยังอยู่ `useState` ข้างในจึงค้างค่าเดิมข้ามสาย

เคยใส่ state `going` ไว้ให้ปุ่มเริ่มโทรยุบหายตอนกด · พอวางสายกลับมาฉากเดิม
ค่ายังเป็น `true` **ปุ่มเริ่มโทรจึงหายถาวรจนกว่าจะรีเฟรช** (เจอ 1 ก.ย. 2026)

**และมันไม่จำเป็นตั้งแต่แรก** — `session.start()` เรียก `onState('connecting')`
เป็นบรรทัดแรกก่อนขอสิทธิ์ไมค์ด้วยซ้ำ ฉาก idle จึงหายทันทีที่กดอยู่แล้ว

**กฎ**: อย่าเก็บสถานะของสายไว้ใน `VoiceCall` · สถานะสายมีที่อยู่เดียวคือ `CallProvider`
ถ้าจำเป็นต้องมี state ในนี้จริง ๆ ต้องล้างมันเมื่อ `call.state` กลับเป็น `idle`

### `animation-fill-mode: both` ทำให้ `position: fixed` ของลูกพัง

เจอบนมือถือจริง 1 ก.ย. 2026 — แสงพื้นหลังของห้องคุยกลายเป็น**กรอบสี่เหลี่ยมกลางจอ**
แทนที่จะเต็มจอ

`.wrap > *` มี `animation: rise-in … both` · `both` ทำให้ transform **ค้างที่เฟรมสุดท้าย
ตลอดไป** ซึ่งคือ `matrix(1,0,0,1,0,0)` — identity ก็จริง แต่ยังนับว่า “มี transform”
ตัวมันจึงกลายเป็น **containing block ของลูกที่เป็น `position: fixed`** อย่างถาวร

**ใช้ `backwards` เมื่อเฟรมสุดท้ายคือค่าปกติอยู่แล้ว** — ได้ผลเหมือนกันระหว่างรอ delay
แต่ปล่อยค่ากลับเป็นปกติเมื่อจบ transform จึงหายไปจริง

**ตรวจยังไง**: `getComputedStyle(el).transform` ต้องเป็น `"none"` ไม่ใช่ `"matrix(1,0,0,1,0,0)"`
สองค่านี้ต่างกันสิ้นเชิงในแง่ containing block ทั้งที่ผลทางสายตาเหมือนกันเป๊ะ

### ห้ามยกลูกขึ้นเหนือ pseudo ด้วย `> * { position: relative }`

กับดักคู่แฝดของข้อบน · เคยเขียน `.talk > * { position: relative; z-index: 1 }`
เพื่อไม่ให้ลูกจมใต้ชั้นแสง — มันไป**ทับ `position: fixed` ของ `.sheet`** ที่อยู่ข้างใน
(specificity เท่ากันแต่กฎนี้อยู่ทีหลัง) แผงตั้งค่าจึงหดมาอยู่ในกรอบ `.wrap` แทนที่จะคลุมเต็มจอ

**ใช้ `isolation: isolate` บนตัวแม่ + `z-index: -1` บน pseudo แทน** — แสงไปอยู่ล่างสุด
ของกล่องนั้นเองโดยไม่ต้องแตะลูกสักตัว · และ `isolation` **ไม่**สร้าง containing block
ให้ `position: fixed` ต่างจาก `transform`

### สีแถบระบบอยู่คนละไฟล์กับพาเลต

`themeColor` ใน `app/layout.tsx` และ `theme_color` / `background_color` ใน
`public/manifest.json` **ไม่ได้อ่านค่าจาก `globals.css`** — เป็นค่าดิบที่พิมพ์ซ้ำไว้สามที่

เคยค้างที่ `#0A0912` ซึ่งเป็นสีพื้น**ก่อน**อุ่นพาเลตเป็น `#120E22` (1 ก.ย. 2026)
ผลคือแถบสถานะกับแถบนำทางของ Android เป็นดำสนิทตัดกับแอปอย่างเห็นได้ชัด
บนเบราว์เซอร์ปกติไม่เห็นเลย **เห็นเฉพาะตอนติดตั้งเป็น PWA แล้วเปิดจากหน้าโฮม**

**แก้พาเลตเมื่อไหร่ ต้องขยับสามค่านี้ตามทุกครั้ง** · และ `background_color`
ใช้ตอนหน้า splash ด้วย จึงควรเป็นสี**พื้น** ส่วน `theme_color` ควรเป็นสี**แถบล่าง**
เพราะแถบนำทางของระบบอยู่ติดกับมันโดยตรง

⚠️ **การเปลี่ยน manifest ต้องถอนแอปออกจากหน้าโฮมแล้วติดตั้งใหม่** ถึงจะเห็นผลครบ
Android แคช manifest ไว้ตั้งแต่ตอนติดตั้ง

### `theme_color` อย่างเดียวไม่พอให้แถบระบบเปลี่ยนสี

ตั้ง `theme_color` แล้วแถบยังเป็นสีเดิมตอนเปิดจากหน้าโฮม — ต้องครบ **สามอย่าง**

1. **`viewport-fit: cover`** — ถ้าไม่มี แอปจะไม่วาดไปถึงใต้แถบของระบบ
   พื้นที่ตรงนั้นระบบจึงวาดเองด้วยสีของมัน · **นี่คือตัวที่ขาดบ่อยที่สุด**
2. **`html` ต้องมี `background` ของตัวเอง** ไม่ใช่ปล่อยให้สืบทอดจาก `body`
   พื้นที่นอกเนื้อหาวาดด้วยสีของ canvas ซึ่งมาจาก `html`
3. `theme_color` / `background_color` ที่ตรงกับพาเลตปัจจุบัน

**ทั้งสามข้อมองไม่เห็นบนแท็บเบราว์เซอร์ปกติ** เห็นเฉพาะตอนติดตั้งเป็นแอปแล้วเปิด
จากหน้าโฮม — ต้องถอนแล้วติดตั้งใหม่ทุกครั้งที่จะตรวจ

⚠️ **ใส่ `cover` แล้วต้องเผื่อ `env(safe-area-inset-*)` เองทุกที่** — `.wrap` เผื่อด้านบน
ส่วน `.nav` กับ `.fab` เผื่อด้านล่างอยู่แล้ว · ถอด `env()` ออกเมื่อไหร่ หัวข้อของทุกหน้า
จะไปอยู่ใต้นาฬิกาของระบบ

⚠️ **แอปที่ติดตั้งแล้วไม่ได้อ่าน manifest สดทุกครั้ง** — ตอนติดตั้ง Chrome ส่ง manifest
ไปให้ Google สร้างเป็น **WebAPK** แล้วฝังค่าสีลงในตัว APK · หลังจากนั้นแอปใช้ค่าที่ฝังไว้
Chrome ตรวจ manifest ประมาณวันละครั้งแล้วค่อยขอ APK ใหม่

**ผลคือแก้สีแล้วในแท็บเบราว์เซอร์เปลี่ยนทันที แต่ในแอปไม่เปลี่ยน** และการถอนแล้ว
ติดตั้งใหม่เร็ว ๆ ก็มักได้ APK ตัวเดิมที่ Google แคชไว้ · ถ้าต้องเห็นผลทันที
ต้อง**ล้างข้อมูลเว็บไซต์ใน Chrome** ก่อนติดตั้ง ไม่ใช่แค่ถอนแอป

⚠️ **ขีดสำหรับปัด (gesture pill) เปลี่ยนสีไม่ได้จากเว็บ** ระบบเลือกขาว/ดำเองตาม
ความสว่างของพื้นหลังที่เราให้ · ที่ทำได้คือทำให้พื้นรอบมันเป็นสีของแอป

### `isolation` บน `.wrap` ทำให้แผงที่เลื่อนขึ้นมาจมใต้แถบล่าง

ใส่ `isolation: isolate` บน `.wrap` เพื่อให้ชั้นแสง `z-index: -1` ไม่จมหายไป —
แต่มันสร้าง stacking context ทั้งก้อน · `.sheet` (z-index 40) ที่อยู่ข้างในจึงถูกขัง
และไปอยู่**ใต้ `.nav` (z-index 20)** ทั้งที่เลขสูงกว่า

**ทางแก้ที่ใช้อยู่: `body` ไม่มี `background` ของตัวเอง พื้นอยู่ที่ `html`**
ชั้นแสงที่ `z-index: -1` จึงยังอยู่หน้าพื้นเสมอโดยไม่ต้องพึ่ง `isolation`

**กฎ**: `.wrap` ต้องไม่สร้าง stacking context — ห้ามใส่ `isolation`, `z-index`,
`transform`, `filter` หรือ `will-change` · ทุกตัวนี้ขังแผงที่อยู่ข้างในเหมือนกันหมด

### `min-height` ทำให้กล่องที่ควรเลื่อนข้างในยืดออกแทน

`.talk` เคยใช้ `min-height: calc(100dvh - 6.25rem)` — **ไม่จำกัดความสูงสูงสุด**
บทสนทนายาวจึงยืดกล่องออกไปเรื่อย ๆ แล้ว `.thread` ที่ `flex: 1` ก็ยืดตาม
จนไม่มีอะไรให้เลื่อนข้างใน กลายเป็น**ทั้งหน้าเลื่อน**แทน

ผลที่เห็นคือข้อความมุดใต้ช่องพิมพ์ที่ลอยอยู่ และมีช่องว่างเปล่าท้ายหน้า
(เจอบนเดสก์ท็อป 1 ก.ย. 2026 · บนมือถือไม่เห็นเพราะบทสนทนายังสั้น)

**ตรวจยังไง**: `document.documentElement.scrollHeight > innerHeight` ต้องเป็น `false`
และ `thread.scrollHeight > thread.clientHeight` ต้องเป็น `true` — ถ้ากลับกันแปลว่า
ตัวเลื่อนอยู่ผิดชั้น

### กล่องที่เลื่อนได้ ระยะเผื่อต้องอยู่นอกตัวมัน

`padding-bottom` ที่ใส่ให้ตัวที่ `overflow-y: auto` เองนับเป็นความสูงของกล่องเลื่อน
**แถบเลื่อนจึงยาวตามลงไปด้วย** ถ้ามีอะไรลอยทับตรงนั้นอยู่ แถบเลื่อนจะโดนบังจนดูเหมือนจมหาย

ระยะเผื่อให้ของที่ลอยอยู่ต้องอยู่ที่ **พ่อของตัวเลื่อน** — `.talk` ไม่ใช่ `.thread`
(เจอบนมือถือ 1 ก.ย. 2026)

### `mask-image` สร้าง containing block เหมือน `filter`

`.thread` ใช้ mask ทำให้ข้อความจางที่ขอบบนล่าง ผลพลอยได้คือลูกที่เป็น `position: fixed`
จะยึดกับ `.thread` แทนที่จะยึดกับ viewport **โดยไม่มี error**
กติกาเดียวกับที่เคยพังจาก `animation-fill-mode: both` ที่ทิ้ง identity matrix ไว้

### ย้ายของเข้าไปห่อรวมกัน = หลุดจาก `gap` ของพ่อเดิม

`.talk__head` กับ `.seg` เคยได้ระยะจาก `gap: 0.9rem` ของ `.talk`
พอเอามาห่อรวมใน `.talk__top` เพื่อให้ลอยค้างด้วยกัน ทั้งคู่ก็หลุดจาก gap นั้น
ระยะกลายเป็น 0 ทันที และ **ไม่มีอะไรฟ้อง** นอกจากตาคน (เจ้าของทัก 1 ก.ย. 2026)
ห่ออะไรใหม่เมื่อไหร่ ให้ตั้ง `gap` ให้ตัวห่อทุกครั้ง

### Next เรียก `startViewTransition` สองครั้งต่อการกดหนึ่งครั้ง

ทุกหน้าเป็น `force-dynamic` การนำทางจึงผ่าน `loading.tsx` เสมอ
Next ทำ view transition **หนึ่งรอบตอน page→โครงร่าง และอีกรอบตอนโครงร่าง→เนื้อจริง**
วัดได้จริงด้วยการ patch `document.startViewTransition` — ห่างกัน ~700ms

ผลคืออะไรก็ตามที่ไม่มี `view-transition-name` ของตัวเองจะติดอยู่ใน snapshot ของ root
แล้วโดน cross-fade **สองรอบ** · แถบล่างเลยกระพริบม่วงสองทีทุกครั้งที่เปลี่ยนหน้า
(เจ้าของทัก 1 ก.ย. 2026)

ของที่ต้องอยู่นิ่งข้ามหน้าต้องตั้งชื่อให้ตัวเองแล้วปิด animation ทั้ง old และ new
**ชื่อห้ามซ้ำกันในหน้าเดียวกัน** ซ้ำเมื่อไหร่เบราว์เซอร์ยกเลิก transition ทั้งชุดเงียบ ๆ

### ชั้นโปร่งแสงที่อยู่ใน snapshot ของ `root` จะกระพริบตอนเปลี่ยนหน้า

`root` มี animation เลื่อน+จางทั้งจอโดยตั้งใจ ระหว่างนั้นภาพเก่ากับภาพใหม่ซ้อนกัน
สำหรับพื้นทึบมองไม่ออก แต่**ชั้นโปร่งแสงจะบวกกันจนสว่างขึ้นแวบหนึ่ง**
แสงพื้นม่วงที่ขอบล่างจึงกระพริบทุกครั้งที่เปลี่ยนหน้า (เจ้าของทัก 1 ก.ย. 2026)

ทางออกคือย้ายชั้นนั้นไปเป็น **พื้นของ `html`** ซึ่งถูกส่งต่อไปวาดบน canvas ของ viewport
และไม่ถูกจับใน snapshot เลย · ต้องคู่กับ `background-attachment: fixed`

**อย่าแก้ด้วยการตั้ง `view-transition-name` ให้ชั้นแสง** — ชั้นที่ตั้งชื่อจะถูกยกขึ้นไป
วาด**เหนือ** snapshot ของ root ระหว่าง transition แสงที่ควรอยู่ล่างสุดจะไปคลุมเนื้อหาแทน
(ตรงข้ามกับแถบล่างที่ตั้งชื่อได้ เพราะมันควรอยู่บนสุดอยู่แล้ว)

### ระยะเผื่อแถบล่างต้องเผื่อ `safe-area` ตามแถบไปด้วย

`.nav` มี `padding-bottom: calc(0.5rem + env(safe-area-inset-bottom))` มันจึง**สูงกว่า
บนมือถือจริง 20–34px** เทียบกับในเบราว์เซอร์เดสก์ท็อป

`.wrap` เคยเผื่อไว้ `5rem` เฉย ๆ — แถวท้ายหน้าจึงมุดอยู่ใต้แถบถาวรบนเครื่องจริง
แล้วตอน `rise-in` มันโผล่ขึ้นมาจากใต้แถบ ซึ่งอ่านเป็นข้อความทะลุออกมาหน้าแถบ
(เจ้าของทัก 2 ก.ย. 2026 · **เบราว์เซอร์ทดสอบไม่มี safe-area จึงไม่มีทางเห็นในเครื่อง**)

และต้องเผื่อ**มากกว่าความสูงแถบอย่างน้อยเท่าระยะที่ `rise-in` ยื่นลง (14px)** ด้วย
ไม่งั้นแถวท้ายจะล้ำเข้าไปในแถบตอนเฟรมแรกของ animation

### `z-index` ไม่ตามไปกับ view transition

`.nav` มี `z-index: 20` ซึ่งใช้ได้ในสภาวะปกติ · แต่พอมันมี `view-transition-name`
ระหว่างเปลี่ยนหน้ามันจะถูกยกออกไปวาดเป็น pseudo layer และ **layer เหล่านั้น
ไม่ได้สืบทอด z-index เดิมมาเลย** ของที่อยู่ใน snapshot ของ root จึงวาดทับแถบได้

ต้องตั้งให้ตรง ๆ: `::view-transition-group(nav) { z-index: 100 }`

## ชั้นเสนอและการเขียนจริง

### เลิกทำที่เขียนค่าตายตัว จะย้อนได้แค่ทางเดียว

`applyDraft` คืน `undo` ให้ปุ่มเลิกทำบนการ์ด · ตอนแรกมันบอกแค่ **ฟิลด์ไหน**
แล้วให้ `undoApply` เขียน `done_at = null` ตายตัว

ใช้ได้กับ "ติ๊กเสร็จ" (ย้อน = ล้างค่า) แต่ **"เอาติ๊กออก" ก็เขียน `null` เหมือนกัน**
การย้อนจึงเขียนค่าเดิมทับตัวเอง · `update` โดนแถวจริง `.select()` ได้แถวกลับมา
ทุกอย่างรายงานว่าสำเร็จ **แต่ไม่มีอะไรเปลี่ยน** และจอขึ้นว่า "เลิกทำแล้ว"

ทางแก้: `UndoTarget` ของการติ๊กพก `prev` (ค่าก่อนเขียน) ไปด้วย ซึ่งอ่านได้ที่
`assertItemAllowed()` เพราะเป็นจังหวะเดียวที่ยังอ่านทันก่อนเขียนทับ

> ⚠️ **การนับแถวไม่ได้พิสูจน์ว่าข้อมูลเปลี่ยน** — มันพิสูจน์แค่ว่าคำสั่งไปโดนแถว
> เขียนค่าเดิมทับค่าเดิมก็ได้แถวกลับมาเท่ากัน · เจอ 4 ก.ย. 2026

### ช่องกรอกที่ไม่มีที่ให้ค่าลง คือข้อมูลที่หายเงียบ ๆ

แผงแก้ร่าง (`DraftCard`) เคยตัดสินว่าจะขึ้นช่องเวลาไหมด้วย
`kind !== 'complete_item' && kind !== 'archive_item'` ซึ่งกว้างเกินไปสองกรณี

| ร่าง | ช่องขึ้น | ค่าที่กรอกไปไหน |
|---|---|---|
| เพิ่ม**โน้ต** | ขึ้น | ไม่ไปไหน — โน้ตไม่มีเวลา (CHECK `shortnote_timeless`) |
| **แก้**ที่ไม่ได้แตะเวลา | ขึ้น | ไม่ไปไหน — `save()` เขียนต่อเมื่อฟิลด์นั้น `!== undefined` |

ไม่มี error ไม่มีอะไรฟ้อง · ผู้ใช้กรอกเวลา กด "เอาตามนี้" แล้วการ์ดเหมือนเดิม

ตอนนี้ `draftTimeField()` ใน `lib/drafts.ts` เป็นคนตัดสินทั้งว่า**ช่องขึ้นไหม**
และ**ค่าลงฟิลด์ไหน** ที่เดียวกัน จึงเถียงกันเองไม่ได้ · มีเทสต์คุมใน `test/drafts.test.ts`

### ชนิดใน schema ของ tool ที่ไม่ตรงกับตัวอ่าน = คำสั่งที่ถูกต้องถูกปฏิเสธเงียบ ๆ

`propose_complete_item` ประกาศ `done` เป็น **`type: 'string'`** แต่ `bool()` ที่อ่านค่า
รับเฉพาะบูลีนแท้ · โมเดลทำตาม schema ส่ง `"true"` มา แล้วโดนปฏิเสธ **ทุกครั้ง**

ไม่มี error ให้ใครเห็น เพราะ `runPropose` คืน `ok:false` เข้าไปเป็นผลของ tool
ตามที่ออกแบบไว้ · สิ่งที่เห็นคือ**พฤติกรรมต่างกันคนละแบบในสองโหมด**

| โหมด | เกิดอะไร |
|---|---|
| แชต | ยิงซ้ำจนบังเอิญส่งบูลีนแท้ · กิน **2–3 รอบจากเพดาน 4** แล้วผ่าน ดูเหมือนปกติ |
| โทร | ยอมแพ้แล้วพูดว่า **"ผมพยายามติ๊กเสร็จให้แล้ว แต่เกิดข้อผิดพลาดบนหน้าจอ"** ทั้งที่ไม่มีการ์ดขึ้นเลย |

> ⚠️ **โหมดแชตที่ผ่านคือสิ่งที่ทำให้บั๊กนี้อยู่รอด** — มันไม่ได้ผ่านเพราะถูก
> แต่ผ่านเพราะมีรอบให้ลองใหม่ · ฝั่งเสียงไม่มีงบรอบขนาดนั้น

ทางแก้สองชั้น — ประกาศ `type: 'boolean'` ให้ตรง **และ** ให้ `bool()` รับสตริง
`"true"`/`"false"` ด้วย เพราะโมเดลส่งบูลีนเป็นสตริงเป็นประจำไม่ว่าจะประกาศชนิดอะไร
มีเทสต์คุมทั้งสองชั้นใน `test/propose.test.ts` (เจอ 4 ก.ย. 2026 จากชุดวัดใน `web/test/accuracy/`)

### ชุดวัดฝั่งโทรใช้ session เดียวทั้งชุด — ด่าน "เรียก tool นี้ไหม" จึงขึ้นกับลำดับเคส

(ต่างจากฝั่งแชตที่ประกอบ `contents` ใหม่ทุกเคส) · บริบทจึงสะสมข้ามเคส —

### ตัวตรวจที่แคบเกิน ตกคำตอบที่ถูก — แก้ได้ แต่ต้องพิสูจน์ว่าของผิดยังตกอยู่

เคส 19 ของชุดวัดหาคำว่า `ดูไม่` · `ส่งใหม่` · `ไม่ได้เก็บ` · โมเดลตอบว่า
*"รูปที่ส่งมาไม่ได้**ถูก**เก็บไว้ ผมดู**ซ้ำ**ไม่ได้แล้ว ส่ง**มา**ใหม่อีกครั้งได้ไหมครับ"*
— ถูกทุกคำ แต่ไม่ตรงสักคำ เพราะมีคำแทรกกลาง

**นี่คือ false negative ของตัวตรวจ ไม่ใช่เหตุให้ผ่อนด่าน** เส้นแบ่งอยู่ตรงนี้:

- ขยายชุดคำแล้ว **ต้องเอาคำตอบที่เคยผิดจริงมายิงซ้ำ แล้วมันต้องยังตกอยู่**
- ถ้าขยายแล้วของผิดผ่านด้วย นั่นคือการผ่อนด่าน ไม่ใช่การแก้บั๊ก

รอบนี้ยืนยันแล้วว่าคำตอบที่แต่งเหตุผลว่า "ในรูปอ่านไม่ชัด" ยังตกเหมือนเดิม
· **ห้ามแก้เทสต์เพื่อให้ผ่าน** แต่ก็ห้ามปล่อยตัวตรวจที่ตัดสินของถูกว่าผิดไว้เฉย ๆ

### กฎที่มีแต่ "ห้าม" โดยไม่บอกทางเดินต่อ จะถูกใช้กว้างเกินเสมอ

แก้เรื่องเดาชื่อวิชากำกวมรอบแรกด้วยการเขียนกฎห้ามล้วน — "ถ้าคำที่เขาพูดตรงกับ
วิชามากกว่าหนึ่งอัน ห้ามเลือกให้เอง ห้ามเรียก `propose_` ในเทิร์นนั้น"

ผลคือ**ถอยหลัง** · ผู้ใช้พูดว่า "วิชาสถาปัตยกรรมเครือข่าย" ซึ่งชี้ไปวิชาเดียวชัดเจน
แต่เพราะมีอีกวิชาที่มีคำว่า "เครือข่าย" อยู่ด้วย โมเดลก็ถามกลับ · เคสที่เคยผ่าน
กลายเป็นไม่ผ่าน ในขณะที่เคสที่ตั้งใจแก้ผ่านพอดี — **นับรวมแล้วเท่าเดิม**

กฎที่ใช้จริงต้องมีสองขา: **ขาที่ให้เดินต่อ** ("ถ้ามีคำที่โผล่ในชื่อวิชาเดียว ใช้อันนั้นเลย")
มาก่อน แล้วค่อยตามด้วย **ขาที่ห้าม** ("ถามเฉพาะตอนที่ไม่มีคำไหนแยกได้เลย")

> ⚠️ **วัดก่อนและหลังเสมอเวลาจูน prompt** — การจูนที่แก้เคสเป้าหมายได้
> แล้วทำเคสข้างเคียงพังคือสิ่งที่มองไม่เห็นถ้าวัดแต่เคสที่ตั้งใจแก้
> เทสต์ใน `test/prompt.test.ts` จึงตรวจว่ามี**ขาที่ให้เดินต่อ**อยู่ด้วย ไม่ใช่ตรวจแต่คำสั่งห้าม

**ตัวอย่างที่สองของกฎเดียวกัน (8 ก.ย. 2026)** — บรรทัด "ห้ามพูดว่าบันทึกให้แล้ว
เพิ่มให้แล้ว หรือเรียบร้อยแล้ว" มีมาตั้งแต่ต้น **แต่โมเดลยังพูดว่า "เรียบร้อยแล้ว" อยู่ดี**
เพราะบรรทัดถัดมาสั่งแบบ*บรรยาย* ("ให้พูดสั้น ๆ ว่าร่างขึ้นบนจอแล้ว") ไม่ได้ให้ประโยค
· พอต้องแต่งเอง ภาษาไทยสุภาพปิดท้ายด้วย "…ให้เรียบร้อยแล้วครับ" เป็นค่าตั้งต้น
— **มันไม่ได้ฝ่าฝืน มันเติมคำปิดท้ายตามธรรมชาติของภาษา**

และคำนั้นเลื่อนจาก*คำเกิน*ไปเป็น*คำโกหก*แค่เปลี่ยนคำนำหน้า:
"ปรับ**ร่าง**ให้เรียบร้อยแล้ว" ยังพอรับได้ · "ปรับ**ข้อมูล**ให้เรียบร้อยแล้ว" คือบอกว่า
ข้อมูลถูกแก้ไปแล้ว ซึ่งไม่จริง · **มันสลับกันเองทุกรอบที่ยิง** ด่านจึงต้องห้ามทั้งคำ

ทางแก้คือ **ยื่นประโยคให้ใช้ตรง ๆ** ทั้งใน prompt และใน `note` ที่ส่งกลับไปกับผลของ
`propose_` · หลังแก้ ฝั่งแชตขึ้นจาก 16/19 เป็น 18–19/19 และทุกเคสตอบด้วยประโยคเดียวกันเป๊ะ

## หลายผู้ใช้ (8 ก.ย. 2026)

> กลายเป็นโค้ดที่ผิดทันทีที่มีคนที่สอง โดยไม่มีบรรทัดไหนเปลี่ยนเลย**

### ด่านที่อยู่ในหน้าเว็บอย่างเดียว ไม่ได้กันอะไรเลย

`supabase.auth.signUp()` เรียกได้จากคอนโซลของใครก็ได้ เพราะ anon key อยู่ใน bundle
ฝั่งเบราว์เซอร์ที่เปิดดูได้อยู่แล้ว · **หน้าจอสมัครไม่ใช่ทางเดียวที่เข้าถึง endpoint นั้น**

ด่านรหัสเชิญตัวจริงจึงเป็น trigger บน `auth.users` ที่ raise เมื่อรหัสไม่ผ่าน
ส่วนการเช็กในหน้าเว็บมีไว้ทำ**ข้อความ**อย่างเดียว เพราะ trigger ที่ raise โผล่มาเป็น
`Database error saving new user` ซึ่งอ่านไม่รู้เรื่อง

> ⚠️ **ห้ามถอดชั้น DB ออกเพราะเห็นว่าหน้าเว็บเช็กแล้ว** สองชั้นนี้ทำคนละหน้าที่

### ตารางความลับต้องเปิด RLS **แล้วไม่ใส่ policy**

`invite_codes` เปิด RLS โดยไม่มี policy สักข้อ = ปิดสนิททั้ง `anon` และ `authenticated`
· ถ้าเผลอใส่ policy แบบ `using (true)` เพราะเห็นว่า "ต้องอ่านได้ตอนสมัคร"
ใครก็ดึงรหัสที่ยังไม่ถูกใช้ไปได้ทั้งกอง · การตรวจรหัสต้องผ่าน `security definer`
ที่คืน **boolean เปล่า ๆ** เท่านั้น ห้ามคืนแถว

### ด่านที่นับ "รวมทุกคน" ทำลายข้อมูลของคนที่ยังไม่พร้อม

Edge Function เคยเช็กว่า "มีเครื่องสมัครรับไหม" **โดยนับรวมทุกคน** แล้วค่อยเรียก
`claim_due_reminders()` ซึ่งอ้างสิทธิ์ทุกแถวของทุกคน

พอมีคนที่สอง: B ลงเครื่องไว้ · A ยังไม่ได้ลง · ด่านผ่านเพราะนับรวมแล้วมีเครื่องอยู่ ·
reminder ของ A ถูกเซ็ต `notified_at` ทิ้งทั้งที่ไม่มีที่ส่ง — **หายถาวร ไม่มี error**

เงื่อนไขต้องอยู่ **ในคำสั่ง `UPDATE` เดียวกับที่เลือกแถว**

```sql
and exists (select 1 from public.push_subscriptions s
             where s.user_id = i.user_id and s.enabled)
```

> ⚠️ **ห้ามย้ายไปกรองที่ Edge Function** เพราะนั่นคือ select แล้วค่อย update
> ซึ่งเป็นกับดักเดิมที่ทำให้ cron รอบที่ทับกันส่ง push ซ้ำ

### `unique` ที่ไม่มี `user_id` อยู่ด้วย

`push_subscriptions.endpoint` เคย unique ทั้งตาราง ซึ่งถูกตอนหนึ่ง endpoint =

ทำให้ผู้ช่วยตาบอดทั้งด้านทันที **โดยไม่มี error** — แค่ตอบว่าไม่มีข้อมูล

### 429 ไม่ได้แปลว่าโควตาหมด

Gemini คืน 429 ทั้งตอนชนเพดาน**ต่อนาที**และตอนหมดโควตา**รายวัน** · เหมารวมเป็น

> ⚠️ **เมื่ออ่านไม่ออกว่าชนอะไร ห้ามเดาว่าเป็นรายวัน** — ความผิดสองแบบราคาไม่เท่ากัน

### `cron.job_run_details` บอกแค่ว่า "ยิงออกไปแล้ว" ไม่ได้บอกว่าปลายทางตอบอะไร

```sql
select status_code, count(*), max(created)
  from net._http_response where created > now() - interval '30 minutes'
 group by status_code;
```

โดยไม่มี error และไม่มีอะไรบนจอบอก**

**กฎ: ลบด้วย `id` เสมอเมื่อคีย์ที่แท้จริงมีหลายคอลัมน์** — ตระกูลเดียวกับ
`unique` ที่ไม่มี `user_id` อยู่ในคีย์

### โชว์ฟิลด์ให้โมเดลเห็น แล้วไม่ยอมรับมันกลับ

tool `projects` โชว์ `รหัสวิชา` (มาจาก `projects.description`) ให้โมเดลเห็นทุกครั้ง
· มันจึงส่งค่านั้นกลับมาเป็นชื่อวิชาเป็นเรื่องธรรมดา — แต่ `findProject()` เทียบ
กับ **ชื่อ** อย่างเดียว ผลคือ `project=MTH102` โดนปฏิเสธด้วย
`หาวิชาชื่อ "MTH102" ไม่เจอ` **ทั้งที่รหัสนั้นถูกต้องและมาจากเราเอง**

ตระกูลเดียวกับ "ชนิดใน schema ของ tool ไม่ตรงกับตัวอ่าน" (4 ก.ย. 2026) — **สิ่งที่
ประกาศออกไป กับสิ่งที่รับกลับ ต้องเป็นชุดเดียวกัน**

⚠️ **รหัสต้องเทียบแบบตรงเป๊ะเท่านั้น** — รหัสวิชาใช้อักษรนำร่วมกันเป็นกอง
(CPE331 · CPE332 · CPE341) เทียบบางส่วนแล้ว "CPE" จะตรงสามวิชา กลายเป็น
ความกำกวมที่เราสร้างขึ้นเอง · มีเทสต์คุมทั้งสามข้อใน `test/propose.test.ts`

### โมเดลเดาชื่อโปรเจกต์ก่อนเรียก `projects` — และ "ทั่วไป" คือคำที่มันเดา

เห็นครั้งแรกที่เคส 02 (8 ก.ย. 2026) และเห็นอีกที่เคส 10 (9 ก.ย. 2026) —
มันส่ง `project=ทั่วไป` หรือ `กิจกรรมทั่วไป` มาก่อนจะเรียก `projects` ดูด้วยซ้ำ
**แกว่งเป็นรอบ ๆ ไม่ใช่พังถาวร** (ยิงซ้ำเคส 10 ได้ 3/3 หลังเห็นมันตกหนึ่งรอบ)

ที่ทำให้มันไม่กลายเป็นข้อมูลผิด คือ **ชั้นเสนอปฏิเสธชื่อที่ไม่มีจริง** แล้วโมเดล
ก็เรียก `projects` ต่อเองแล้วส่งใหม่ให้ถูก · **ทางฟื้นตัวนี้จะหายทันทีถ้าวันหนึ่ง
`findProject()` ถูกทำให้ "ใจดี" ขึ้นจนเดามาแล้วเข้าใกล้พอก็ผ่าน**

⚠️ เวลาที่เจอเคสตกด้วยเหตุ "ลงผิดโปรเจกต์" ให้ยิงซ้ำก่อนสรุปว่าถอยหลัง
