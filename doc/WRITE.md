## 1 · ปัญหาที่แก้

ตอนนี้ผู้ช่วยในแอป **อ่านอย่างเดียว** ส่วนการเขียนไปทาง MCP บน claude.ai
เหตุผลเดิมสมเหตุผลตอนวางแผน แต่ของจริงคือ **เจ้าของใช้บนมือถือ** และวินาทีที่นึกออก
ว่าต้องเพิ่มงานคือตอนเดินออกจากห้องเรียน ไม่ใช่ตอนนั่งหน้าคอม

ประตูที่เขียนได้จึงอยู่ผิดที่มาตลอด

## 2 · หลักการเดียวที่ทุกอย่างตามมา

> **โมเดลไม่เขียน โมเดลเสนอ**

ชั้น tool ยังไม่มีทางเขียนลง DB เหมือนเดิม · tool ตัวใหม่แค่คืน "ร่างการกระทำ"
กลับมาให้เว็บวาดเป็นการ์ด · **การเขียนจริงเกิดที่ server action ที่ผู้ใช้กดยืนยัน**

ผลพลอยได้ที่สำคัญ: `test/guard.test.ts` **ไม่ต้องแก้เลย** ถ้าออกแบบถูก
ถ้าวันไหนต้องแก้เทสต์นั้นเพื่อให้ผ่าน แปลว่าเดินผิดทางแล้ว

## 3 · ทำไมต้องยืนยัน ไม่ให้เขียนตรง ๆ

| เหตุ | รายละเอียด |
|---|---|
| ASR ไทยพลาดที่ตัวเลข | "ส่งวันที่ 4" กับ "วันที่ 14" ต่างกันหนึ่งพยางค์ · รหัสห้อง "E11-S604" ยิ่งหนัก |
| Live API ไม่มีจังหวะทาน | โมเดลตอบเร็วมาก กว่าจะรู้ว่าผิดก็เขียนไปแล้ว |
| ของจริงมีผลจริง | นี่คือตารางเรียนจริง ผิดแล้วไม่ใช่ข้อมูลเพี้ยน แต่**พลาดส่งงาน** |
| ห้องเรียนมีเสียงรบกวน | จุดที่จะใช้เสียงมากที่สุดคือจุดที่ ASR แม่นน้อยที่สุด |

## 4 · ขอบเขต — แบ่งตามความเสี่ยง

| ระดับ | การกระทำ | ให้ทำไหม | ชั้นกัน |
|---|---|---|---|
| ย้อนได้ทันที | ติ๊กเสร็จ · เลิกติ๊ก · เลื่อนเวลา · เปลี่ยนชื่อ | **ได้** | ยืนยัน 1 ครั้ง + แถบเลิกทำ |
| สร้างของใหม่ | เพิ่มงาน · เพิ่มเตือน · เพิ่มโน้ต · เพิ่มกิจกรรม | **ได้** | ยืนยัน 1 ครั้ง |
| ย้ายที่ | ย้าย item ข้าม project | **ได้** | ยืนยัน 1 ครั้ง (ย้ายกลับได้) |
| เก็บเข้าคลัง | `archived_at` ของ item/event | **ได้** | ยืนยัน 1 ครั้ง · มีสายพานลบ 7 วัน กู้คืนได้ |
| **ทำลาย** | ลบ project · ลบถาวร · ล้างประวัติ | **ไม่ให้เลย** | ไม่มี tool ให้เรียก |

**เส้นที่ไม่ข้าม** — `projects` มี `on delete cascade` ลบวิชาเดียวแล้ว items หายทั้งกอง
คำสั่งเสียงที่ฟังผิดคำเดียวไม่ควรมีอำนาจนั้น แม้จะมี confirm ก็ตาม
ถ้าอยากลบวิชาจริง ๆ ให้ทำในหน้าคลังด้วยมือ ซึ่งเห็นทั้งกองก่อนตัดสินใจ

**`project_schedules` ก็ไม่ให้แตะ** — ตารางเรียนซ้ำทุกสัปดาห์เป็นโครงที่ทุกอย่างอ้างอิง
แก้ผิดหนึ่งแถวแล้วผิดทั้งเทอมโดยไม่มีอะไรฟ้อง

## 5 · สถาปัตยกรรม

```
พูด/พิมพ์
   ↓
Gemini (Live หรือ chat)  ── เรียก tool ที่ขึ้นต้นด้วย propose_*
   ↓
lib/ai/tools.ts           ── ตรวจรูปแบบ + เติมค่าที่ขาด + คืน "ร่าง"   ← ไม่แตะ DB
   ↓
ฝั่งเว็บ                   ── วาดการ์ด · ผู้ใช้กดยืนยัน
   ↓
app/actions/propose.ts    ── server action · ตรวจสิทธิ์เอง · เขียนจริง   ← จุดเดียวที่เขียน
   ↓
Supabase (RLS ของผู้ใช้)
```

### tool ที่เพิ่ม

| tool | คืนอะไร |
|---|---|
| `propose_add_item` | ร่างงาน/เตือน/โน้ต — ชื่อ · project · เวลา · ชนิด |
| `propose_update_item` | ร่างการแก้ — id เดิม + ฟิลด์ที่เปลี่ยน + **ค่าเดิมคู่กัน** |
| `propose_complete_item` | ติ๊กเสร็จ/เลิกติ๊ก |
| `propose_archive_item` | เก็บเข้าคลัง |
| `propose_add_event` | ร่างกิจกรรมครั้งเดียว |

**ทุกตัวคืน `draft` ที่มี `id` ชั่วคราวของตัวเอง** เพื่อให้พูดแก้ต่อได้
("เปลี่ยนเป็นวันศุกร์" → โมเดลเรียก `propose_update_draft` กับ id นั้น ไม่ใช่สร้างใบใหม่)

### สิ่งที่ร่างต้องมีเสมอ

- **ชื่อ project แบบเต็ม ไม่ใช่ id** — ผู้ใช้ต้องทานได้ว่าไปลงถูกวิชา
- **เวลาแบบอ่านออก** `พฤ 4 ก.ย. 23:59` ไม่ใช่ ISO
- **ค่าเดิมคู่กับค่าใหม่** สำหรับการแก้ ไม่งั้นทานไม่ได้ว่าเปลี่ยนอะไร
- **แหล่งที่มา** ประโยคที่ทำให้เกิดร่างนี้ เผื่ออ่านแล้วงงว่ามาจากไหน

> ⚠️ **07 สูงกว่าทุกแบบ** — กล่องคำบรรยายบวกร่างบวกปุ่มสามใบ · บนเครื่องเตี้ย
> มันจะดันปุ่มวางสายลงไปจนตกขอบจอ **ต้องคุมความสูงด้วย `max-height` + ให้ตัวร่าง
> เลื่อนในตัวเอง ไม่ใช่ปล่อยให้ฉากยืด** และวัดบนจอ 360×640 ก่อนถือว่าเสร็จ
>
> ⚠️ **02 บังแถบล่าง** — ในหน้าอื่นระหว่างสาย ผู้ใช้อาจกำลังจะกดเปลี่ยนหน้าพอดี
> ต้องมีปุ่ม "ไว้ก่อน" ที่ยุบแผ่นลงเป็นแถบบาง ไม่ใช่บังค้างจนกว่าจะตัดสินใจ

**สามอย่างที่ห้ามโดนบังระหว่างสาย** — ปุ่มวางสาย · ตัวจับเวลา · วงเสียง
(อย่างหลังคือสิ่งเดียวบนจอที่บอกว่าไมค์ยังทำงาน)

## 8 · สิ่งที่ต้องระวัง

**`VISIBLE_AREAS` ผูกกับชื่อ Area** — ร่างที่ชี้ไป Area ที่ผู้ช่วยมองไม่เห็น
ต้องถูกปฏิเสธที่ server action ด้วย ไม่ใช่เชื่อว่าโมเดลจะไม่เสนอ

**ร่างมีอายุ** — ร่างที่ค้างเกินหนึ่งสายไม่ควรยืนยันได้อีก เพราะบริบทเปลี่ยนไปแล้ว
เก็บใน state ฝั่งเว็บอย่างเดียว **ไม่ต้องลง DB** หายไปพร้อมการรีเฟรชคือพฤติกรรมที่ถูก

**สายหลุดกลางร่าง** — Live API ตัดที่ 15 นาทีแล้วต่อใหม่ · ร่างต้องรอดข้ามการต่อสาย
เพราะมันอยู่ฝั่งเว็บ ไม่ได้อยู่ในสาย

**เขียนแล้วต้องเห็นผลทันที** — `router.refresh()` หลังยืนยัน ไม่งั้นผู้ใช้กดซ้ำเพราะคิดว่าไม่ติด

**โควตา** — tool call กินโควตาเหมือนข้อความปกติ · การเสนอ-แก้-ยืนยันหนึ่งรอบ
อาจกิน 3–4 turn ซึ่งมากกว่าการถามเฉย ๆ
