01หลักการเดียวที่ทุกอย่างตามมา

โมเดลไม่เขียน โมเดลเสนอ

ชั้น tool ยังไม่มีทางเขียนลง DB เหมือนเดิม · tool ตัวใหม่แค่คืน “ร่างการกระทำ” กลับมาให้เว็บวาดเป็นการ์ด — การเขียนจริงเกิดที่ server action ที่คุณกดยืนยัน

ผลพลอยได้ที่เป็นเครื่องวัดว่าเดินถูกทาง: test/guard.test.ts ไม่ต้องแก้เลย — ถ้าวันไหนต้องแก้เทสต์นั้นเพื่อให้ผ่าน แปลว่าเดินผิดแล้ว

02ทำไมต้องยืนยัน

สี่เหตุผล ซึ่งข้อสุดท้ายเป็นข้อที่หนักที่สุด

เหตุรายละเอียด
ASR ไทยพลาดที่ตัวเลข“ส่งวันที่ 4” กับ “วันที่ 14” ต่างกันหนึ่งพยางค์ · รหัสห้องอย่าง E11-S604 ยิ่งหนัก
Live ไม่มีจังหวะทานโมเดลตอบเร็วมาก กว่าจะรู้ว่าผิดก็เขียนไปแล้ว
ของจริงมีผลจริงนี่คือตารางเรียนจริง ผิดแล้วไม่ใช่ข้อมูลเพี้ยน แต่พลาดส่งงาน
ที่ที่จะใช้มากสุดคือห้องเรียนและทางเดิน — จุดที่มีเสียงรบกวนมากที่สุด และ ASR แม่นน้อยที่สุด

06ลำดับการทำ

ทำแชตก่อนเสียงเสมอ — ทานง่ายกว่า ผิดแล้วเห็นชัดกว่า และไม่กินโควตาเสียง

  1. ฐาน ยังไม่มีหน้าจอ

    server action ชุดเขียน พร้อมตรวจสิทธิ์และนับแถวที่เขียนจริง · เทสต์รวมเคส “ไม่ใช่ของเรา” และ “ไม่มีแถวให้แก้” · ตัวประกอบร่างที่ไม่แตะ DB

    เสร็จเมื่อ · เรียก action จากเทสต์แล้วข้อมูลเปลี่ยนถูก และ guard.test.ts ยังผ่าน
  2. การ์ดในโหมดแชต

    tool propose_add_item ตัวเดียวก่อน · การ์ดแบบ 07 ในสายข้อความ · แถบเลิกทำหลังเขียนสำเร็จ

    เสร็จเมื่อ · พิมพ์ว่า “เพิ่มงานส่งรายงาน Network พฤหัสหน้า” แล้วกดยืนยัน งานโผล่ในหน้าวันนี้
  3. การ์ดระหว่างสาย

    แบบ 07 ใน VoiceCall พร้อม max-height ที่วัดแล้ว · พูดแก้ร่างได้ · ร่างค้างข้ามหน้าด้วยแบบ 02

    เสร็จเมื่อ · พูดขณะเดินกลับหอแล้วงานลงถูก โดยไม่ต้องหยุดเดิน
  4. ที่เหลือ

    tool ครบชุด · การ์ดซ้อนเมื่อเสนอหลายใบ · ชั้นสองแบบ 10 · อัปเดตเอกสารทั้งชุด
